# Оркестрация нескольких агентов через коннектом

Статус: спецификация следующего расширения, **не реализовано**.
Версия: 1.0 · 16 октября 2026.
Нормативная связь: [Plan.md §100](../Plan.md#100-оркестрация-нескольких-агентов).
Механизм исполнения проверок и вычисления вердикта задан в
[спецификации модуля тестирования](testing-module.md) (Plan §101). Он обслуживает
review/integration и ORC-13, сохраняя различие успеха проверки и успеха repair.
При противоречии сохраняются ограничения безопасности, биологической топологии
и исследовательской приёмки из §§29–30,37–39,46,57–62,97–99 основного плана.

## 1. Результат для пользователя и границы

Пользователь задаёт цель, выбирает проект, состав команды, лимиты и степень
самостоятельности. FlyCode разбивает работу на проверяемые задачи, вызывает
подходящих агентов, передаёт им необходимые результаты, управляет очередью и
объединяет проверенные изменения. Пользователь видит, кто работает, над чем,
почему задача получила приоритет, сколько ресурсов осталось и что мешает завершению.

FlyCode сам является Hermes — средой размещения и управления агентами.
Коннектом направляет выбор стратегии и назначений; семантический разбор выполняют
LLM, а реальные вызовы, разрешения и фиксацию результатов обеспечивает диспетчер.
Нейронная рекомендация не является ни системным разрешением, ни доказательством
корректности результата. Биологические названия ниже обозначают вычислительную
интерпретацию, а не доказанную функцию мозга в программной инженерии.

Первая поставка: одно локальное рабочее пространство, один активный workflow
(общая пользовательская цель), до четырёх экземпляров агентов, локальные модели
LM Studio. Несколько агентов могут пользоваться одной моделью с разными ролями
и контекстами; это не означает четыре одновременно загруженные модели.
Многопользовательский SaaS, удалённые исполнители и произвольные плагины не входят
в первую поставку. Облачный провайдер подключается отдельным этапом с явным
разрешением на передачу конкретного проекта этому провайдеру.

Требования помечены идентификаторами `ORC-*`; слово «должен» означает обязательную
приёмку, а не описание уже доступного API.

## 2. Термины и команда агентов — ORC-01

| Сущность | Значение |
|---|---|
| Модель | Конкретный inference endpoint и model ID, например Qwen или Jev |
| Профиль агента | Роль, инструкция, способности, модель, разрешённые инструменты и лимиты |
| Экземпляр агента | Изолированный запуск профиля с собственными состоянием, памятью и задачей |
| Workflow | Цель пользователя, граф задач, общий бюджет, журнал и критерии завершения |
| Задача | Проверяемая единица работы с входами, зависимостями и ожидаемыми артефактами |
| Попытка | Одно назначение задачи одному экземпляру; повтор создаёт новый attempt ID |
| Артефакт | Версионированный результат: отчёт, patch, test report или решение о проверке |

Начальная команда:

| Роль | Назначение | Начальное подключение | Право менять проект |
|---|---|---|---|
| Планировщик | Разложить цель, предложить зависимости и критерии | Qwen 3.5 9B | Нет |
| Исследователь | Найти код, проверить предположения, подготовить контекст | Qwen 3.5 9B | Нет |
| Разработчик | Подготовить ограниченный patch для одной задачи | Qwen 3.5 9B | Только изолированная копия |
| Проверяющий | Проверить patch и отдельно запустить обязательные проверки | Qwen 3.5 9B + runner проверок | Не редактирует проверяемый patch |
| Оценщик вариантов | Оценить кандидатов назначения и ожидаемую стоимость | Jev-Style-Qwen3.5-2B-Decision-G | Нет инструментов и дочерних агентов |

Jev может остаться модельной ролью общего cortex; отдельный постоянно работающий
экземпляр для него не обязателен. Диспетчер не является ещё одним LLM-агентом.
Профиль не считается способным к задаче только из-за выбранного имени роли:
реестр хранит заявленные capabilities и измеренные результаты отдельно.
Проверяющий с теми же весами, что разработчик, имеет отдельный контекст и роль,
но не считается статистически независимым экспертом.

При регистрации сервер проверяет доступность модели, схему ответа, ограничения
контекста и разрешения. Неизвестный или недоступный model ID виден как причина
недоступности; скрытая замена другой моделью запрещена. Версия профиля и его
инструкция входят в идентичность запуска. Общие модельные клиенты не должны
сбрасывать счётчики и память соседних экземпляров.

## 3. Два уровня управления — ORC-02

```text
Цель пользователя → предложение плана LLM → проверенный граф задач
                                             ↓
                                 очередь готовых задач и ресурсов
                                             ↓
                      кандидаты диспетчеризации → коннектом → арбитр
                                             ↓
                                назначения / сообщения / отмена
                                             ↓
                         изолированные циклы исполнителей и моделей
                                             ↓
                      артефакты → проверка → интеграция → новый контекст
```

Верхний уровень выбирает задачу, агента, допустимый размер контекста и необходимость
проверки/перепланирования. Нижний — существующий цикл предложения и выполнения
инструментов внутри назначенной задачи. Оба уровня проходят собственные маски
разрешений. Схема свободного обмена «каждый агент вызывает любого» откладывается:
она даёт больше автономии, но усложняет бюджет, восстановление и контроль циклов.
В первой версии вся связь проходит через центральный диспетчер.

Состояние управляющего коннектома принадлежит workflow и изменяется одним
последовательным циклом событий. Параллельные ответы агентов не вызывают
`brain.step()` конкурентно. У каждого исполнителя отдельный контроллер нижнего
уровня; коннектом верхнего уровня не разделяет с ними изменяемый neural state.
Наблюдающий коннектом получает тот же поток фактических событий, но не выполняет
альтернативные назначения при нулевом влиянии.

## 4. Разбиение цели и жизненный цикл — ORC-03

Планировщик предлагает DAG — граф без циклов. Каждая задача содержит цель,
проверяемые критерии, зависимости, класс capabilities, границы чтения/изменения,
исходную ревизию, бюджет и ожидаемые артефакты. Диспетчер проверяет отсутствие
циклов, существование зависимостей и реализуемость бюджета до постановки в очередь.
Неопределённость, существенно меняющая результат, порождает вопрос пользователю;
независимые задачи могут продолжаться, зависимые ждут ответа.

Состояния задачи:

`planned → ready → assigned → running → awaiting_review → succeeded`.

Дополнительные переходы: `blocked`, `retry_wait`, `failed`, `cancelled`.
`blocked` всегда имеет машинную причину и условие разблокировки; отсутствие
GPU-слота оставляет задачу `ready` и не считается неудачей агента.
`running → awaiting_review` требует артефакт, но не утверждение самого автора
об успехе. `awaiting_review → succeeded` требует проверок из критериев задачи.
Отрицательный review переводит задачу в `retry_wait` либо `failed` при исчерпании
попыток. Зависимые задачи становятся готовы только после `succeeded` всех
обязательных зависимостей. Неудача обязательной зависимости блокирует потомков,
а не помечает их успешно пропущенными.

Workflow имеет состояния `draft`, `running`, `pausing`, `paused`, `cancelling`,
`succeeded`, `incomplete`, `failed`, `cancelled`. Пауза прекращает новые вызовы,
дожидается или ограничивает текущие согласно timeout и фиксирует checkpoint.
Отмена распространяется на дочерние попытки; поздний ответ сохраняется как
отклонённый, но не меняет проект. `succeeded` разрешён только после интеграции
артефактов, прохождения общих проверок и отсутствия незавершённых обязательных задач.
Исчерпание бюджета без результата даёт `incomplete`, а не успешное завершение.

Новые подзадачи и перепланирование создают новую версию DAG. Базовые критерии
пользователя нельзя удалять ради зелёного статуса. Удаление обязательной проверки,
расширение доступа или увеличение бюджета требуют прямого решения пользователя.
Завершённые результаты сохраняют исходные связи с версиями плана.

## 5. Кандидаты диспетчеризации и коннектом — ORC-04

Вводится отдельный контракт `DispatchCandidate`, а не новое строковое имя
в существующем `VALID_TOOLS`. Действия верхнего уровня:

| Действие | Эффект |
|---|---|
| `assign` | Назначить готовую задачу подходящему свободному агенту |
| `request_review` | Создать проверку конкретного hash артефакта |
| `deliver_message` | Передать разрешённое сообщение указанному получателю |
| `retry` | Создать новую ограниченную попытку с причиной |
| `replan` | Запросить предложение новой версии графа |
| `wait` | Ждать конкретное событие/ресурс до известного времени |
| `escalate` | Запросить решение пользователя при блокировке |
| `cancel_attempt` | Отменить попытку и отозвать её право записи |
| `finalize` | Завершить workflow после независимого completion gate |

Свободный текст LLM не может породить вызов агента. Диспетчер исполняет только
валидный кандидат, присутствующий в текущем снимке, с совпадающей версией графа,
очереди и бюджета. Повторная проверка разрешений и резервирование ресурсов
происходят атомарно перед вызовом. Устаревший кандидат пересчитывается.

Предлагаемый `OrchestrationStimulusV1` кодирует размер/возраст очереди, зависимости,
прогресс критического пути, доступные ресурсы, остаток бюджета, ошибки, риск,
новизну и признаки каждого кандидата. При большом графе используется ограниченная
выборка до четырёх допустимых кандидатов за такт; ротация включает старейшие задачи,
чтобы дешёвый предварительный отбор не исключал их навсегда. Общий backlog
остаётся виден в агрегатах. Вектора имеют версионированные размеры, нормализацию
и ограничения finite; существующие 13 входных признаков полного графа не
переиспользуются молча для новых семантических значений.

Контроллер возвращает отдельный score для **ID каждого кандидата**, уверенность
и режим поведения. `action_bias` по названию инструмента не заменяет выбор пары
«задача–агент». Сопоставление признаков с нейронными входами/выходами версионировано,
проверяется экспериментально; исходная биологическая смежность не изменяется.
Full/Reduced/Functional варианты сравниваются с одинаковым контрактом и бюджетом.

Интерпретация механизмов: Task Compass удерживает корневую цель и критический путь;
MB хранит опыт пары «семейство задачи–профиль»; valence/RPE учитывают проверенный
прогресс и стоимость; habituation снижает повтор одинаковых неудачных назначений;
novelty допускает ограниченную проверку новой стратегии. Эти механизмы дают
предложения, а не права расширить разрешения или исчерпать бюджет экспериментами.
Параллельные события получают sequence number; offline replay использует именно
этот порядок. Семантический смысл назначений оценивается LLM и проверками.

## 6. Приоритеты и планирование ресурсов — ORC-05

Перед ранжированием исключаются задачи с незавершёнными зависимостями,
несовместимой ролью/версией входа, недостаточным бюджетом, отозванным доступом,
конфликтующим правом записи или недоступным endpoint. Только затем считается score.

Начальная проверяемая baseline-формула, не утверждение об оптимальности:

`base = .30P + .20C + .15U + .15A + .10G − .05K − .05R`.

Все признаки нормированы в [0,1]: P — приоритет пользователя (0..3 / 3),
C — доля разблокируемого обязательного пути, U — близость указанного пользователем
срока, A — время ожидания / 10 минут с насыщением, G — ожидаемый полезный прогресс,
K — доля расходуемого оставшегося бюджета, R — оценённый риск. Без срока U=0;
просрочка отмечается в UI, но не отменяет остальные ограничения.
Прогноз G не считается фактическим результатом.

В допущенном bias-режиме: `score = base + .2 × influence × clip(fly_score, −1, 1)`.
Все веса, влияние и порядок разрешения равенства входят в снимок политики.
При равных score выбираются более старая задача, затем стабильный candidate ID.
Пользователь может изменить приоритет или приостановить задачу; изменение
записывается и учитывается в следующем такте. Running-задача не прерывается
посреди потенциально изменяющего действия только из-за нового приоритета.

Для защиты от голодания каждый восьмой успешный dispatch отдаётся старейшей
допустимой ожидающей задаче, если она попала в текущий набор; выборка обязана
включить её в такой такт. Коннектом не отменяет эту гарантию. Счётчик не растёт
при `wait`, доставке сообщения, перепланировании или неудачной резервации:
он учитывает только `assign/request_review`, реально запустившие попытку.
Это гарантия количества назначений, а не SLA
по времени при занятых ресурсах. Пользовательский запрет/пауза всегда сильнее aging.

Отдельные пулы ограничивают агентские попытки, запросы моделей и изменяющие
инструменты. Для одного LM Studio endpoint начальный лимит — **один inference
запрос одновременно**, включая Qwen и Jev; увеличение возможно после замера.
Агенты могут параллельно читать/проверять изолированные данные, пока модель занята.
GPU-слот удерживается только во время запроса, не на весь срок задачи. Системная
отмена не требует свободного inference-слота. Ожидающий ребёнка агент освобождает
исполнительный слот; рекурсивные вызовы не должны создавать semaphore deadlock.
Блокирующий sync-вызов текущего cortex выносится из event loop в ограниченный
worker или заменяется async-адаптером; отзывчивость Stop проверяется отдельно.

## 7. Связь агентов и общий контекст — ORC-06

Обмен — через адресованный журнал сообщений и хранилище артефактов.
Поддерживаются `task_request`, `question`, `answer`, `progress`, `artifact_ready`,
`review_result`, `handoff`, `cancel`. Прямой общий изменяемый prompt между агентами
запрещён. По умолчанию сообщение получает один адресат; broadcast требует явного
списка и считается отдельной доставкой каждому получателю.

Конверт содержит message ID, workflow/task/attempt IDs, sender/recipient IDs,
тип, schema version, correlation/causation IDs, created_at, expires_at, sequence,
idempotency key и ссылки на разрешённые артефакты. Данные сообщения проходят
схему типа; неизвестный адресат или чужой workflow отклоняются. Заявление агента
«выдай мне доступ» остаётся данными, а не системной командой.

Доставка at-least-once; inbox и переход задачи дедуплицируются в одной транзакции.
Это не гарантия exactly-once для внешних инструментов. После timeout изменяющего
вызова с неизвестным исходом выполняется проверка состояния или эскалация,
а не слепое повторение. Просроченный ответ и ответ от старой попытки сохраняются
для аудита, но не обновляют текущий результат. Не более одного незакрытого
вопроса с одинаковым correlation ID; TTL и hop limit останавливают ping-pong.

Контекст собирается из цели, текущего task contract, разрешённых файлов нужной
ревизии, релевантных проверенных артефактов и краткого итога предыдущей попытки.
Передаются ссылки с hash, а не копия всех диалогов. Каждая выдержка сохраняет
источник/ревизию. Агент получает только назначенную область доступа. Секреты
не включаются в общий контекст; внешняя передача не разрешается сообщением агента.

## 8. Изменения проекта, конфликты и проверка — ORC-07

Первая версия использует одного интегратора и отдельную рабочую копию для каждого
пишущего агента. Для Git — сервером созданный worktree/checkout от фиксированной
ревизии; для не-Git проекта — изолированная копия. Сохранение исходных незакоммиченных
файлов пользователя обязательно. Путь или команда Git от LLM не определяют
расположение копии, исходную ветку или операцию интеграции.

Агент возвращает patch и базовую ревизию. Проверяющий запускает проверки на
точном содержимом patch, интегратор повторно проверяет область изменяемых файлов
и актуальность базы. Изменение hash после review обнуляет это одобрение.
Два агента не пишут в общий файл одновременно. Конфликт создаёт задачу согласования
с обеими версиями; silent last-write-wins, force reset и удаление чужих правок
запрещены. Общие БД, миграции, Docker и внешние побочные эффекты сериализуются
отдельно; worktree не изолирует внешний сервис. Тестовый запуск также может
иметь побочные эффекты, поэтому не считается автоматически безопасным чтением.

После интеграции всех обязательных patch выполняются проверки объединённого
проекта, даже если каждая отдельная ветка была зелёной. Старый независимый patch
можно использовать повторно только при проверенной совместимости новой базы;
зависимые тестовые результаты считаются устаревшими. Проверяющий не может
подменить patch своим исправлением без новой попытки и повторной проверки.

## 9. Бюджет, отмена и восстановление — ORC-08

Начальные предлагаемые лимиты одного workflow:

| Лимит | По умолчанию |
|---|---:|
| Активные экземпляры | 4 |
| Задачи в графе, включая review/retry-подзадачи | 64 |
| Глубина декомпозиции / детей одного узла | 3 / 8 |
| Попытки одной задачи | 3 |
| Перепланирования одного workflow | 2 |
| Суммарные модельные запросы / инструменты | 60 / 120 |
| Общий wall-clock / timeout одного inference | 30 минут / 120 секунд |
| Доставки сообщений / размер конверта | 200 / 16 KiB |
| Hop limit цепочки сообщений / TTL вопроса | 4 / 5 минут |
| Одновременные получатели broadcast | 3 |
| Доля бюджета на обязательную проверку | 20% |

Это настройки нового workflow, не изменения уже существующих defaults одиночного
агента. Родитель резервирует дочерний бюджет атомарно; сумма потраченного,
зарезервированного и свободного согласуется с общим лимитом по каждой аддитивной
величине (запросы, инструменты, при наличии учёта — токены). Wall-clock — отдельный
общий deadline с первого запуска; длительности параллельных попыток не складываются
как прошедшее время. Пауза не сбрасывает deadline; возобновление после него даёт
`incomplete`. Считаются все Qwen/Jev/planner/reviewer запросы, повторы и ошибки
провайдера. Неизвестный расход
после обрыва помечается uncertain и консервативно удерживается в резерве до
сверки. Неиспользованный резерв освобождается, фактически потраченное не возвращается
при отмене или retry. Три попытки включают исходное назначение. Дочерний агент
не может создать себе новый бюджет. Резерв проверки не используется разработчиком;
его недостаточность даёт `incomplete`.

Лимит токенов задаётся дополнительно только при доступном учёте usage; при
отсутствии токенизации нельзя обещать точный токенный лимит. Деньги показываются
только при известной тарификации провайдера; локальные вызовы не получают
выдуманную нулевую стоимость ресурсов. UI всегда показывает запросы и время.

Диспетчер хранит состояния, outbox/inbox, права записи, резервы и события
транзакционно в SQLite. Heartbeat попытки — каждые 10 секунд; lease — 30 секунд.
Потеря lease отзывает право фиксации, но сама по себе не доказывает остановку
процесса. Новая пишущая попытка стартует только после подтверждения остановки
старой; fencing token проверяется перед применением patch. Внешний эффект с
неизвестным исходом требует reconcile. Никакой автоматический retry не восстанавливает
отозванный доступ.

При перезапуске менеджера активные попытки сначала получают статус `reconciling`;
LLM-запросы заново автоматически не отправляются. После сверки сохраняется
прогресс, неопределённые эффекты видны пользователю. Старый мозговой снимок
загружается только при совпадении topology/checkpoint/encoder schema/policy.
При несовместимости используется явный reset в baseline-режим с событием;
это не восстановление эквивалентной нейронной траектории.

## 10. Разрешения и допуск коннектома — ORC-09

Разрешённые инструменты, файлы, модели и права каждой попытки — пересечение
прав пользователя, workflow, профиля и task contract. Делегирование не расширяет
ни один из этих наборов. Сервер проверяет канонические пути и symlink перед
чтением, записью и выдачей артефакта; ID не даёт доступа к соседнему проекту.
`postgres_query` и `http_request` оцениваются по операции,
а не по названию категории `READ_TOOLS`. Эффекты внутри изолированной копии и
во внешнем мире проверяются отдельно. Журнал не публикует секретные данные.

Текущий допуск Phases 13–14 относится к одиночным учебным траекториям и
диагностическому вмешательству. Он **не разрешает** multi-agent назначения,
параллельные записи, новый scheduler или новые модели.

Новый admission format v2 должен связывать класс решения `orchestration`, версию
диспетчера/encoder/message schema, идентичность графа и checkpoint, состав и
версии профилей, model IDs/endpoint policy, набор инструментов, параллелизм,
бюджеты, семейства задач, seeds и исходные trajectories. В implementation fingerprint
включается новый пакет orchestration. Endpoint identity не гарантирует неизменность
весов: если checksum/revision модели не доступен, это ограничение фиксируется,
а исследовательская переносимость между заменами весов не заявляется.

Порядок допуска: baseline → zero-influence shadow → ограниченное влияние на
назначения чтения/анализа → изменение пишущих назначений → проверенный hard-режим
только в измеренном scope. Ступени 0/.1/.25/.5/1 имеют смысл лишь вместе с классом
решений: 100% bounded correction не равно hard selection. Каждая ступень требует
парных запусков и фактических изменений назначений; отсутствие вмешательств
не доказывает безопасность следующей ступени. Нельзя называть сырое hard-исполнение
проверенным режимом через переименование конфигурации.

Ошибка коннектома, nonfinite score, повтор ID, превышение разрешённого риска
или неуспешное изменённое назначение переводят верхний уровень в фиксированный
baseline до конца workflow с причиной в журнале. Ошибка отдельного инструмента
без причинной связи с изменённым назначением не считается доказанным вредом
нейронной политики. Независимый safety/budget veto остаётся обязательным.

## 11. Функции, повышающие ценность — ORC-10

| Функция | Пользовательский результат | Ограничение и проверка |
|---|---|---|
| Режим «план без запуска» | Видны команда, DAG, бюджет, зависимости и риски до расхода моделей исполнителей | Изменяющих вызовов нет; прогноз стоимости помечен оценкой |
| Критический путь и объяснение блокировок | Видно, что задерживает готовый результат и кого стоит подключить | Причина ссылается на реальную зависимость/ресурс/событие |
| Передача задачи другому агенту | Можно заменить застрявшего исполнителя без потери проверенных результатов | Новая попытка, ограниченная выжимка, отзыв старого права записи |
| Пакет результата | Итоговый patch, команды проверок, отчёты, расходы и связь с задачами | Каждый вывод содержит источник и hash; непроверенное отмечено |
| Контрольные точки и возобновление | Можно пережить закрытие приложения без повторной оплаты уже завершённого | Reconcile не повторяет неизвестный внешний эффект |
| Переиспользование проверенного опыта | Меньше повторного поиска и одинаковых ошибок в похожих задачах | Cache key включает проект/ревизию, входы, версии профиля/модели/инструментов и разрешения |
| Сравнение двух решений по запросу | Две изолированные попытки для сложной подзадачи и общий тест выбора | Общий бюджет, максимум две ветви, явное резервирование перед стартом |

Cache не переносит секреты или артефакты между проектами автоматически.
Cache hit не считается новым независимым успехом агента. Несогласие проверяющих
порождает конкретный контрпример/проверку или вопрос пользователю; большинство
голосов не заменяет тесты. Адаптация предпочтений учитывает только проверенный
результат и фактическую стоимость; нельзя вознаграждать самоотчёт «готово».
Обновляемая память профиля изолирована по проекту/версии/seed; frozen evaluation
и наблюдатель её не изменяют. Online learning включается отдельным измеряемым
этапом после базового scheduler, не автоматически вместе с orchestration.

Credit assignment связывает проверяемый эффект с dispatch decision, задачей,
попыткой и hash результата. Принятый отчёт и реально интегрированное исправление
имеют разные сигналы; самоотчёт, истечение таймера или совпадение рекомендаций
не дают награду за завершение. Поздняя регрессия относится к породившей её версии
артефакта, а не ко всем параллельным агентам. Правило распределения отложенной
награды, ограничение обновления и откат снимка фиксируются до эксперимента.

## 12. Контракты и проектируемая поверхность управления — ORC-11

Все перечисленные ниже модели/API — **предлагаемые**, в текущем коде их нет.
Сохраняются Pydantic v2 и разделение domain, policy, runtime и telemetry.

| Контракт | Обязательные группы полей |
|---|---|
| `AgentProfile` | id/version, role, model binding, instruction hash, capabilities, tool/file policy, limits |
| `WorkflowSpec` | id/version, goal, project snapshot, acceptance checks, profiles, budget, execution policy |
| `WorkItem` | id/version, parent, dependencies, objective, capabilities, input artifact hashes, read/write scopes, priority, state, acceptance checks |
| `AgentAttempt` | id, task/plan version, profile version, status, lease/fencing token, reserved budget, model calls, timestamps, error |
| `AgentMessage` | envelope из §7, типизированное содержимое, разрешённые ссылки |
| `ResultArtifact` | id/version/hash, kind, producer attempt, base revision, storage ID, validation state, provenance |
| `DispatchCandidate` | id, operation, task/agent IDs, snapshot version, expected progress/risk/cost, deadline |
| `DispatchDecision` | candidate IDs и scores, baseline/proposed/executed IDs, mode/influence, veto/fallback reason, budget reservation, admission ID |

Структурные изменения графа используют expected version; mismatch даёт conflict,
а не перезапись нового состояния. Сервер генерирует IDs и storage paths.
Артефакт состояния `AgentAttempt` допускает `reconciling` отдельно от состояния
задачи; сетевой сбой агента не меняет состояние соседних задач.

Проектируемые локальные API, не существующие маршруты:

| Маршрут | Назначение |
|---|---|
| `GET/POST /api/agents` | Каталог и регистрация разрешённого профиля |
| `POST /api/workflows` | Создать draft/предложить план; повтор с тем же idempotency key возвращает исходный workflow |
| `GET /api/workflows/{id}` | Версионированный снимок плана, очереди, расходов и результатов |
| `POST /api/workflows/{id}/commands` | `start/pause/resume/cancel/set_priority/reassign`; schema, expected_version и idempotency key обязательны |
| `GET /api/workflows/{id}/events` | SSE с sequence/cursor, восстановлением после переподключения |
| `GET /api/workflows/{id}/artifacts/{artifact_id}` | Только разрешённый артефакт по серверному ID |

Остаются loopback/origin/session-token ограничения текущего API. Профиль не может
задавать произвольный URL, shell command или путь к секрету из браузера: endpoint
выбирается из серверного реестра. Существующие `/api/runs` и одиночный CLI сохраняют
совместимость и прежнее значение допусков. Импорт старой истории не превращает
её в многоагентный workflow с придуманными участниками.

## 13. Интерфейс наблюдения — ORC-12

Главный экран сохраняет привычный диалог. Рядом доступны:

- «План»: задачи, зависимости, приоритет, приёмка, блокировки; изменение приоритета
  и безопасная пауза задачи, передача другому профилю.
- «Команда»: роль, текущая задача, модель, состояние, последние подтверждённые
  действия; различаются «модель отвечает», «ожидает GPU», «ждёт результат коллеги».
- «Связь»: адресованные вопросы, передачи и ссылки на результаты; видны отправитель,
  получатель, задача и статус доставки. Повтор доставки не создаёт вторую карточку.
- «Контроллер»: baseline, рекомендация коннектома, фактически выполненный выбор,
  понятные причины/ограничения и событие возврата к baseline. Визуализация графа
  задач не выдаётся за изображение активных нейронов.
- «Ресурсы»: израсходовано, зарезервировано, доступно; время, очередь endpoint,
  отдельный резерв проверки. Остановка и бюджет всегда доступны на мобильном экране.
- «Результат»: объединённый patch и проверки, незавершённые пункты, ограничения.

Показываются цели, краткие обоснования решений, действия и проверяемые результаты.
Скрытые внутренние рассуждения модели не являются требуемым интерфейсом.
Процент прогресса считается по выполненным взвешенным обязательным задачам;
изменение знаменателя при новой версии DAG показывается явно. При отсутствии
оценок используются количества задач и состояние, без выдуманного ETA.

## 14. Измерения и критерии приёмки — ORC-13

Сравнить: текущий одиночный агент; multi-agent с FIFO/capability baseline;
multi-agent с обычным приоритетным scheduler; Functional/Reduced/Full scheduler;
нейронный scheduler с абляцией MB/novelty/habituation. Для вывода о пользе
коннектома состав команды, модели, данные, инструменты, стартовая память и
суммарные бюджеты одинаковы. Разницу в параллелизме и параметрах измерять отдельно.
Zero-shadow не даёт counterfactual success; нужны реальные парные исполнения.

Минимальная матрица: шесть семейств × три seeds = 18 случаев на вариант:
независимые поиски с общим итогом; зависимая реализация; конфликтующие patch;
отрицательный review/регрессия после интеграции; дефицит endpoint/бюджета;
сбой процесса/повтор сообщения/неизвестный исход внешнего действия.
Во всех случаях реальные файловые операции и проверки, а отказы инфраструктуры
инъецируются явно и отмечаются. Дополнительно нужны невиденные реальные проекты
перед заявлением об общем преимуществе; синтетическая матрица их не заменяет.

Обязательные проверяемые сценарии:

| ID | Приёмка |
|---|---|
| AC-01 | DAG с циклом/неизвестной зависимостью отклоняется до вызова агента; независимые узлы выполняются разрешённо параллельно |
| AC-02 | Назначения соответствуют capabilities/правам; делегирование не расширяет доступ; два профиля одной модели не делят память/счётчики |
| AC-03 | Старейшая готовая задача получает защищённое назначение на восьмом dispatch; заблокированная не занимает слот |
| AC-04 | Повтор message/command не создаёт новую попытку или повторное изменение; старый/просроченный ответ не принимается |
| AC-05 | Совокупные spent/reserved/free согласованы при гонке двух назначений; резерв проверки и лимит endpoint не превышены |
| AC-06 | Конфликт patch виден; чужие/незакоммиченные файлы сохранены; одобрение другого hash не применяется; итоговые тесты реально выполнены |
| AC-07 | Пауза/Stop не запускают новые запросы, endpoint wait не блокирует отмену; поздний ответ не меняет проект |
| AC-08 | Перезапуск в любой точке отправки/получения/интеграции восстанавливает очередь без слепого повторения внешнего эффекта |
| AC-09 | Duplicate IDs/nonfinite/ошибка мозга вызывают baseline; veto сильнее любого score; старый одиночный допуск не разрешает dispatch |
| AC-10 | При influence=0 совпадают назначенные задачи, агенты и исполняемые действия с baseline при фиксированном тестовом порядке событий; ошибки наблюдателя не меняют их |
| AC-11 | Context/cache не раскрывает чужой проект/секрет, сохраняет provenance и инвалидируется при изменении входов/прав/модели |
| AC-12 | SSE после reconnect восстанавливает историю без дублей, mobile controls доступны, фактический и предложенный выбор различимы |
| AC-13 | Ни дочернее «готово», ни голосование моделей не завершают workflow без обязательных acceptance checks |
| AC-14 | Одновременные agent/question/retry/replan действия достигают лимитов без рекурсивной лавины и semaphore deadlock |

Метрики: доля проверенного завершения (все ошибки остаются в знаменателе),
wall-clock и inference time, model/tool calls и usage, время очереди p50/p95,
блокировки, конфликты/повторы, нарушения бюджета, проверенные регрессии,
ложное завершение, доля вмешательств/fallback, время диспетчеризации и нагрузка
самого коннектома. Speedup не засчитывается, если скрыто увеличено число моделей
или суммарных запросов. Качество результата и стоимость публикуются вместе.

Для первого узкого допуска: все 18 сценариев завершены согласно ожидаемому
контракту (в том числе корректная остановка в failure-сценариях), ноль нарушений
доступа/бюджета/ложного успеха, ни одного дополнительного сбоя относительно
baseline, полные traces и минимум 30 сопоставимых dispatch decisions. Для
продвижения уровня нужны минимум 10 фактически изменённых низкорисковых назначений
в матрице и отсутствие дополнительных регрессий; 10 — инженерный smoke-порог,
не статистическое доказательство безопасности. Общий выигрыш заявляется только
по заранее объявленным метрикам, парным исходам, повторным seed и интервалам
неопределённости. Отрицательный или нулевой результат сохраняется.

| 20 — Рабочее пространство команды | План/команда/связь/ресурсы в UI, команды пользователя и пакет результата; сравнение альтернатив и cache после базовой приёмки | ORC-10..12; AC-07,11,12; desktop/mobile QA |

Связь зависимостей: 15 → 16 → 17 → 18 → 19; UI-обзор и события появляются с
фазой 15, затем расширяются в фазе 20. Cache и сравнительные ветви не блокируют
первую проверяемую оркестрацию и имеют собственный расход бюджета.

Предлагаемые места реализации: `domain/orchestration.py` (контракты), новый пакет
`orchestration/` с модулями registry, workflow, scheduler, messages, resources,
workspace и store; `policy/orchestration.py` (маска и ранжирование),
`brain/orchestration.py` (encoder/readout), расширения `research/` и
`research/validation.py` для новых admission/экспериментов, существующие `web/`
и `telemetry/` для отображения. Эти файлы ещё не созданы; их точное разбиение
фиксируется в отдельном плане реализации после выбора первой поставки.
Существующий `run_agent` подключается адаптером исполнителя; он не превращается
в монолитный scheduler. Исторические данные и существующие contracts сохраняют
версии; миграция не изменяет исходные журналы одиночных запусков.

## 16. Пример полного сценария

Запрос: «Добавить фильтр заказов по статусу и проверить совместимость API».

| Задача | Исполнитель | Зависимости | Результат |
|---|---|---|---|
| T1: изучить контракт API | Исследователь | Нет | Текущие поля, ограничения и проверяемый контракт фильтра |
| T2: изменить обработчик | Разработчик A | T1 | Patch только разрешённых файлов обработчика |
| T3: подготовить проверки | Разработчик B | T1 | Patch тестов по контракту, включая неизвестный статус |
| T4: проверить решения | Проверяющий | T2, T3 | Проверка точных hash обоих patch в общей тестовой копии |
| T5: интегрировать и завершить | Диспетчер/интегратор | T4 | Объединённый patch, финальные проверки и пакет результата |

Коннектом выбирает между готовыми назначениями T2 и T3 с учётом ресурсов и
приоритета. На одном LM Studio запросы моделей идут по очереди, хотя работа с
изолированными файлами может перекрываться. Это не обещание ускорения от двух
профилей на одном GPU. T4 не начинается на неполных входах.

Если T2 застряла, пользователь видит конкретный сбой и остаток бюджета.
Допустимы ограниченный retry или передача другому разрешённому профилю; T3
не выполняется повторно без изменения её входов. Старый экземпляр T2 теряет
право фиксации. Если проверка T4 обнаружила ошибку контракта, создаётся новая
версия зависимых задач; исходные критерии пользователя сохраняются.

До старта и при каждом изменении в UI видны DAG, роли, основания назначения,
предложение коннектома, фактический выбор и расходы. Окончательное «Выполнено»
появляется после T5, а не после сообщения разработчика «код готов».
