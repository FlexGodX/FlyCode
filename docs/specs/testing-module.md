# Модуль тестирования и доказуемой проверки результата

Статус: частичная реализация начальной фазы 21; общий модуль ещё не принят.
Доступны snapshot, зарегистрированный pytest runner, evidence/verdict и CLI
`flycode verify --repo PATH`. Карта пользовательских критериев, baseline/target/
integration планы, остальные runners, runtime recovery, API/UI и командный gate
остаются в [плане поставки](../superpowers/plans/2026-10-16-specification-delivery.md).
Версия: 1.0 · 16 октября 2026.
Нормативная связь: [Plan.md §101](../Plan.md#101-модуль-тестирования-и-проверки-результата).
Интеграция: [оркестрация агентов](connectome-orchestration.md), ORC-07..13.
Ограничения безопасности, неизменности биологической топологии и честного
сравнения из основного плана сохраняются.

## 1. Назначение и текущая граница — TST-01

Модуль отвечает на вопросы: соответствует ли результат задаче, не сломаны ли
прежние функции, надёжно ли отработала команда агентов и есть ли измеренная
польза от выбранного контроллера. Пользователь получает проверенный результат
с воспроизводимыми свидетельствами либо конкретную причину, почему проверка
не закончена. Зелёный ответ LLM не является результатом тестирования.

Проверяются три независимые области:

| Область | Предмет | Результат |
|---|---|---|
| Проект | Patch, API, UI, сборка, миграции и интеграция изменений | Вердикт по критериям пользовательской задачи |
| FlyCode | Контракты, инструменты, очереди, связь агентов, бюджеты и восстановление | Отчёт о соответствии программной реализации |
| Исследования | Одиночные/командные агенты, baseline, коннектомы, обучение и абляции | Экспериментальные метрики и ограниченный допуск |

Эти отчёты не взаимозаменяемы. Зелёные unit-тесты FlyCode не доказывают успех
пользовательской задачи; успешный repair не доказывает превосходство коннектома.

В текущем коде есть `tools/tests.py:run_tests` (pytest и разбор текстового итога),
`Observation.is_healthy`, telemetry, benchmark/adaptation/shadow и scoped validation.
Предлагаемый модуль объединяет их свидетельства через адаптеры; он не считается
готовым на основании наличия этих команд. Первые поддерживаемые исполнители:
pytest, зарегистрированные build/lint/typecheck-профили, HTTP health/contract
проверки, Docker/PostgreSQL и browser acceptance. Дополнительные языки подключаются
через явный профиль runner, без распознавания произвольной shell-команды от LLM.

## 2. Архитектура и границы ответственности — TST-02

```text
Task / patch / workflow / experiment
                  ↓
         VerificationPlan + SubjectSnapshot
                  ↓
    policy + budget + environment preflight
                  ↓
       VerificationEngine → isolated RunnerAdapter
                  ↓                ↓
           trusted supervision ← raw observations
                  ↓
       normalizer → immutable evidence bundle
                  ↓
          deterministic VerdictEvaluator
                  ↓
    completion gate / research admission / UI report
```

| Компонент | Ответственность |
|---|---|
| PlanBuilder | Собрать утверждённые обязательные проверки и дополнительные предложения |
| SnapshotManager | Зафиксировать код, входы, зависимости и тестовые контракты |
| VerificationEngine | Очередь проверок, зависимости, лимиты, отмена и жизненный цикл |
| RunnerAdapter | Выполнить один зарегистрированный тип проверки и вернуть наблюдения |
| SandboxManager | Выдать изолированное окружение, разрешённые ресурсы и очистить только принадлежащее запуску |
| OracleRegistry | Хранить версионированные критерии и независимые способы проверки результата |
| ResultNormalizer | Проверить структуру отчёта, идентичности тестов, счётчики и полноту |
| VerdictEvaluator | Вычислить итог по фиксированным правилам, без обращения к LLM |
| EvidenceStore | Неизменяемые артефакты, manifest, контрольные суммы и связи с исходным запуском |
| ExperimentAdapter | Передать фактические метрики в существующий research и будущий admission v2 |

Агент-тестировщик — клиент этого сервиса: предлагает случаи, пишет дополнительные
тесты в разрешённой копии, анализирует ошибки. Он не получает право менять
обязательные критерии, manifest исполнителя или итоговый вердикт. Диспетчер
оркестрации владеет DAG задач и общим бюджетом; VerificationEngine владеет только
графом проверок конкретного плана и не создаёт конкурирующий scheduler агентов.
Коннектом может предложить порядок/набор дополнительных проверок, но не подавить
обязательную проверку, превратить ошибку в успех или подписать собственный допуск.

## 3. Объект проверки и контракты — TST-03

Все перечисленные модели предлагаются для реализации на Pydantic v2.
Идентификаторы и пути хранения создаёт сервер.

| Контракт | Обязательные поля и смысл |
|---|---|
| `SubjectSnapshot` | project/workflow/task/attempt IDs, Git base при наличии, manifest всех разрешённых входных файлов и их SHA-256, dirty/untracked inventory, snapshot hash |
| `VerificationPlan` | id/version, subject hash, acceptance contract hash, profile versions, required/optional checks, dependencies, limits, retry policy, environment policy |
| `CheckSpec` | id/version, runner/profile ID, target IDs, required flag, oracle version, expected outcome, timeout, resource class, allowed effects |
| `CheckAttempt` | id, check/plan IDs, attempt number, state, lease/fencing token, sandbox ID, start/end, process exit, resource accounting, error class |
| `CaseResult` | runner + suite + case/parameter/repeat identity, outcome, duration, assertion/diagnostic refs, collection provenance |
| `EvidenceManifest` | schema version, subject/plan/oracle/runner hashes, environment identity, actual invocations, expected/observed case IDs, artifact hashes, completeness/redaction flags |
| `VerificationVerdict` | subject/plan IDs, status, required coverage, reasons, failed/unknown criteria, evidence ID/hash, evaluator version, evaluated_at |
| `ExperimentEvaluation` | experiment identity, preregistered matrix, case outcomes, denominators, matched/unmatched resources, aggregate metrics, uncertainty and scope |

Снимок включает незакоммиченные изменения и разрешённые untracked-файлы;
одного commit SHA недостаточно. Проверяются фактически исполняемые байты.
Секреты не копируются в manifest или отчёт. Разрешённые secret bindings
идентифицируются opaque version ID; неизвестная версия внешнего ресурса отмечается
как ограничение воспроизводимости. Зависимости фиксируются lock/hash или фактически
установленными версиями; неполный fingerprint не называется точным воспроизведением.

Критерии приёмки и обязательные тесты принадлежат пользователю/доверенному профилю,
отдельно от изменяемого агентом кода. Проверки, созданные агентом, хранятся как
новая версия с указанием автора попытки и источника требования; они не заменяют
прежние тесты автоматически. Изменение обязательного контракта требует решения
пользователя и нового плана. Переименование/удаление случая не стирает старый failure.

## 4. План проверок и качество тестов — TST-04

План содержит базовую проверку до изменения, целевые проверки patch, регрессионный
набор и проверку объединённого результата. Дополнительные проверки выбираются
по изменённым компонентам и зависимостям. При неизвестной карте зависимостей
обязательный регрессионный набор расширяется, а не исключается на основании
мнения LLM. Отсутствующий runner или исходные данные дают явную блокировку.

Каждый обязательный критерий связан хотя бы с одним наблюдаемым oracle:
assertion, внешний запрос, состояние БД, проверка файла, build artifact или UI-
действие с ожидаемым результатом. Есть позитивные, негативные и граничные случаи.
Тест существующего поведения проверяется на базовом снимке; regression test
исправляемой ошибки должен воспроизводить дефект до patch и проходить после него.
Для новой функции исходное отсутствие реализации допускается, но чувствительность
проверки подтверждается отрицательным примером или контролируемым дефектом.

Проверяется поведение, а не совпадение реализации с самим тестом. Например,
«переиспользован общий helper» требует наблюдаемого вызова helper, а не только
правильных чисел. Для важных правил используются выбранные mutation-проверки:
выключение валидатора, игнорирование фильтра, подмена return value. Неубитая мутация
показывает пробел проверки; mutation score не подменяет выполнение требований.
Мутации выполняются только в отдельных копиях и учитываются в бюджете.

Обязательная карта покрытия: requirement ID → check ID → case IDs → evidence.
Строковое покрытие и число зелёных тестов показываются дополнительно; они
не считаются самостоятельным доказательством правильности задачи.

## 5. Исполнение, состояния и остановка — TST-05

План: `draft → queued → preparing → running → evaluating → completed`.
Дополнительные состояния: `blocked`, `cancelling`, `cancelled`, `interrupted`.
`completed` означает окончание вычисления вердикта, а не успешную проверку.
Попытка проверки: `queued/preparing/running/collecting/finished` либо
`blocked/cancelled/interrupted/reconciling`. Результат попытки хранится отдельно
от технического состояния процесса.

Preflight проверяет snapshot, доверенный profile ID, разрешённые эффекты, ресурсный
резерв, доступность зависимостей и совместимость версий. Он не запускает модели
для угадывания недостающей конфигурации. Runner получает argv из серверного
профиля, типизированные параметры и канонический target внутри snapshot;
`sh -c` и клиентская строка команды не являются интерфейсом модуля.

Проверки имеют deadline и отдельный timeout запуска/подготовки. Отмена прекращает
новые назначения, останавливает принадлежащую попытке группу процессов и ждёт
подтверждения завершения. Grace period — 5 секунд, затем принудительное завершение
разрешено только для принадлежащих sandbox процессов. Внешний эффект с неизвестным
исходом отмечается unknown и сверяется, а не повторяется автоматически.

Перезапуск менеджера переводит активные попытки в `reconciling`; новые попытки
создаются после проверки старых процессов/артефактов и отзывов lease. Старый
worker не может дописать результат после нового fencing token. Частичный отчёт
не становится полным после перезапуска. Поток событий восстанавливается по cursor.

## 6. Изоляция и доверие — TST-06

Тесты исполняют код проекта и потенциально меняют файлы, БД и сеть. Первая
поставка использует изолированную копию snapshot и отдельное процессное окружение
для доверенных локальных проектов. Режим hostile/untrusted требует отдельной
песочницы с проверяемыми ограничениями; worktree и процесс сами по себе не являются
границей безопасности. Если необходимый режим изоляции недоступен, запуск блокируется.

Sandbox-профиль определяет read/write roots, сеть, CPU/RAM, число процессов,
диск, доступные исполняемые файлы и secret bindings. Для untrusted-профиля:
нет домашней папки, SSH/API credentials, host Docker socket, произвольных host
mounts и production БД; сеть по умолчанию закрыта. Ограничения контейнера должны
реально обеспечиваться платформой. Контейнер не называется абсолютной защитой.

Docker/PostgreSQL/HTTP проверки получают уникальные имена ресурсов, сеть, тестовые
учётные данные и порты. Миграции выполняются на одноразовой БД. Browser-проверки
используют отдельный профиль, только разрешённые origins и данные сценария.
Очистка проверяет ownership labels/run ID; нельзя удалять чужие контейнеры,
тома, браузерные профили или незакоммиченные файлы пользователя.

Служебные manifests и VerdictEvaluator находятся за пределами изменяемой копии
агента. Отчёт runner и stdout рассматриваются как входные данные: ограничиваются
размер, пути вложений, типы, счётчики и количество записей. XML-парсер не разрешает
DTD/external entities. HTML-артефакты не исполняются в основном UI.
Защита от symlink/path traversal проверяется при выдаче и записи артефактов.

Даже защищённый файл теста не делает in-process pytest достоверным против
злонамеренного кода того же процесса: код может влиять на runtime проверки.
Для таких угроз нужны внешние black-box oracles и отдельная доверенная граница
наблюдения. Проверки доступа/бюджета FlyCode наблюдаются доверенным supervisor,
а не сообщением тестируемого агента. Уровень доверия указывается в каждом отчёте;
структурно правильный JUnit не объявляется криптографическим доказательством истины.

## 7. Результаты и правила вердикта — TST-07

Статусы отдельных случаев: `passed`, `failed`, `error`, `skipped`, `xfail`,
`xpass`, `timeout`, `cancelled`, `unknown`. Ошибка assertion отличается от сбоя
подготовки, collection, инфраструктуры или parser. Ни одна из этих причин
не исчезает из отчёта из-за отсутствия стандартного summary.

Raw outcome runner сохраняется отдельно от выполнения ожидаемого контракта:
например, намеренно падающий negative control подтверждает чувствительность
oracle, но остаётся падением исполняемого теста и не считается успешным repair.

Итоговый статус:

| Статус | Обязательное условие |
|---|---|
| `passed` | Все обязательные критерии подтверждены допустимыми oracle на текущем snapshot; отчёт полный; ограничения не нарушены |
| `failed` | Есть подтверждённое нарушение обязательного критерия либо наблюдённая запрещённая операция |
| `inconclusive` | Для обязательного критерия нет достоверного ответа: timeout, error, missing/skip/xfail, flaky, неполная среда/отчёт |
| `cancelled` | Проверка отменена; частичные наблюдения и уже известные нарушения сохраняются |
| `invalidated` | Код, критерии, зависимости, среда или идентичность проверенного результата изменились после его проверки |

При полном прогоне подтверждённый failure имеет приоритет над inconclusive;
при отмене/инвалидации известные failures остаются отдельными причинами. Требуемая
проверка не может исчезнуть из знаменателя. Optional failures видны отдельно;
они не отменяют mandatory pass только если план заранее объявил их
неблокирующими. Нарушение доступа/бюджета всегда блокирует независимо от optional.

Нулевой exit code необходим для обычного pytest-pass, но недостаточен. Пустой
набор, все skipped/xfail, collection mismatch, missing report или противоречащие
exit/status данные не дают `passed`. Unexpected pass (`xpass`) обязательного
известного дефекта требует пересмотра ожидания и повторной проверки новым планом.
Baseline failures фиксируются до patch; их наличие не разрешает новый ущерб и
не даёт общего pass. Успешный целевой тест на уже сломанной базе может дать
ограниченный verdict по своему критерию, но не зелёный workflow.

Каждый вердикт связывается с subject hash, планом, runner/oracle/evaluator versions
и средой. Интеграция или изменение входов инвалидирует применимые результаты.
Совпадающий patch hash на другой базе сам по себе не сохраняет одобрение.
Полный workflow завершается только по актуальному объединённому snapshot.

## 8. Нестабильность и повторные запуски — TST-08

Повтор assertion failure не используется для поиска случайного зелёного результата.
Диагностические rerun имеют заранее заданный предел: максимум две дополнительные
попытки на check; все исходы сохраняются. Различающиеся pass/fail дают `flaky`,
который отражается как отдельный признак CaseResult и `inconclusive` для обязательного
критерия. Один удачный rerun не заменяет первое падение. Infra retry допускается
только по policy и при известном безопасном состоянии ресурсов.

Случай нельзя автоматически отправить в quarantine, сделать optional или снизить
ожидания после падения. Quarantine — версионированное решение владельца контракта
с причиной и сроком пересмотра; отсутствие обязательного свидетельства по-прежнему
блокирует завершение. Для стохастических свойств план заранее задаёт число повторов,
seeds, метрику и порог с неопределённостью, вместо обычного «одного зелёного теста».

Replay с записанными ответами моделей проверяет обработку событий и политику,
но не является новым реальным inference или независимым успешным repair.
Mock-исполнители маркируются; их результат не даёт допуск к реальному endpoint.

## 9. Проверка оркестрации — TST-09

Модуль исполняет AC-01..14 из спецификации оркестрации как версионированные
сценарии. Детерминированный event harness управляет часами, порядком ответов,
доставкой и отказами. Отдельные live-сценарии проверяют реальные процессы,
файлы, локальные модели и конкурентные ресурсы. Один deterministic trace
не доказывает корректность всех порядков выполнения.

Обязательные инварианты проверяются после каждого перехода: нет назначения до
зависимостей, расширения прав, двойного владельца записи, принятия устаревшего
patch, превышения spent+reserved, повторного эффекта от duplicate command,
ложного завершения или скрытого пропуска обязательной проверки.

Fault injection задаётся до прогона: задержка/дубликат/потеря ответа, падение
worker/менеджера до и после записи outbox/inbox, потеря lease, недоступная модель,
занятый endpoint, конфликт patch, corrupt artifact, отказ БД и нехватка бюджета.
Инъекция записывается вместе с ожидаемым безопасным исходом. Корректная остановка
при намеренном отказе — успех сценария надёжности, но не successful repair.

Для zero-influence shadow сравниваются реальные выбранные назначения и действия
с baseline при фиксированном расписании событий. Для live-concurrency публикуются
расписание/trace и разброс, без обещания побитового повторения wall-clock.
Проверяющий агент не изменяет собственные критерии и не завершает workflow
до контрольной проверки объединённого результата модулем тестирования.

## 10. Проверка коннектома и экспериментов — TST-10

Адаптеры используют существующие `research/benchmark.py`, `adaptation.py`,
`perturbation.py`, `shadow.py`, `validation.py`, а не создают независимые копии
метрик. Раздельно хранятся: успех сценария тестовой инфраструктуры, успешный
repair/workflow, безопасность и исследовательское преимущество.

Проверяются topology hash и исходные neuron IDs, finite состояния/score,
неизменность frozen policy, сохранение и изоляция обучаемой памяти, ограничение
обновлений, rollback, кандидатные bias по ID, действительный уровень вмешательства
и сохранение safety mask. Lesion меняет оговорённые параметры существующего графа,
а не незаметно заменяет его синтетической сетью. Недоступный реальный датасет даёт
blocked/skip с причиной, а не выдаёт случайный reservoir за биологический запуск.

До эксперимента фиксируются варианты, задачи и их семейства, seeds, train/validation/
held-out split по исходному проекту/семейству, метрики, бюджеты и stopping rule.
Дубликаты одного задания не считаются независимыми отложенными задачами.
Если held-out использован для настройки, следующая заявка на обобщение требует
нового неиспользованного набора. Критерии и приватные oracle не передаются агентам
как готовые ответы; разрешённая публичная инструкция остаётся одинаковой.

Все варианты имеют одинаковые модели/инструменты/стартовую память и суммарные
лимиты; различия параметров, состояния, GPU/CPU, параллелизма, training budget
и задержки отражаются явно. Если ресурсы не сопоставимы, matched-compute claim
не разрешён. Ошибки setup, timeout, missing checkpoint и незавершённые случаи
остаются в объявленной матрице; исключение случая требует отдельного изменённого
отчёта с причиной и не заменяет исходный знаменатель.

Минимум multi-agent smoke/admission остаётся 18 сценариев на вариант, три seeds,
30 dispatch decisions и условия ORC-13; это не доказательство общего преимущества.
Для сильного исследовательского вывода ориентир текущей методологии — минимум
10 различных задач и 5 seeds на вариант, парные исходы, интервалы неопределённости,
робастность и специфичные абляции. Эти объёмы — нижняя граница покрытия, не
гарантия статистической мощности. Агрегаты строятся по задачам/семействам, а не
по тысячам коррелированных шагов как независимым наблюдениям.

Отчёт хранит эффект и неопределённость выбранной метрики, все raw outcomes,
расходы и null results. Shadow agreement не превращается в counterfactual success.
Допуск вычисляется отдельным policy gate из фактических артефактов; `passed`
тестового модуля сам по себе не создаёт admission. Форматы v1/v2 и их scope
остаются различными; замена runner/oracle/evaluator, модели, топологии, бюджета
или scheduler требует совпадающих свежих свидетельств.

Режимы из [спецификации выбора моделей](model-selection.md) (Plan §102)
проверяются раздельно: single без наличия/запросов Jev, dual с фактическим учётом
обеих ролей и другая совместимая модель из общего каталога. Их model identity
и область допуска не смешиваются. MS-01..12 задают дополнительные проверки
изолированного выбора моделей и отдельных кнопок интерфейса.

Для [таск-трекера](task-tracker.md) (Plan §103) дополнительно проверяются TT-01..16:
конкурентное получение одной задачи, связь instance→task, согласованность проекций,
lease/reconciliation, revisions и завершение только по актуальному verdict.
Зелёная карточка UI сама по себе не считается свидетельством выполненной проверки.

## 11. Хранение, воспроизведение и отчёты — TST-11

Для плана создаётся bundle: subject/plan manifests, перечень случаев и attempts,
argv/profile identity, зафиксированная среда, stdout/stderr, структурированные
результаты, traces, логи сервисов, patches и при необходимости screenshot/browser
trace. У каждого артефакта — ID, размер, hash, origin и redaction policy.
Вердикт ссылается на завершённый manifest, опубликованный атомарно после проверки
полноты. Запись ведётся append-only по attempt ID; новый rerun не перезаписывает
первый результат. Manifest/артефакты не могут ссылаться за разрешённый root.

Метаданные/очередь — SQLite; большие файлы — серверное artifact storage. При
совместной работе с orchestration используются отдельные таблицы/владельцы
записи и связанные IDs, а не конкурентные копии состояний задач. Выдача одобрения
и чтение его потребителем проверяют свежесть snapshot/version; изменившийся
проект проверяется заново, без окна «проверили одно — применили другое».

Секреты удаляются до сохранения пользовательских логов и экспортов; redaction
не считается безошибочным детектором. Минимизация доступа и одноразовые credentials
остаются основной защитой. Если без скрытых данных результат невоспроизводим,
указывается ограничение. Публичный экспорт не содержит приватные пути, проект,
исходники или сырые trace без отдельного разрешения пользователя на публикацию.
Hash связывает содержимое, но не удостоверяет честность злонамеренного владельца
всех локальных файлов; этот предел явно указан в admission/evidence.

Повтор из bundle использует новую попытку, проверяет доступность/версии ресурсов
и не воспроизводит внешние изменяющие действия автоматически. Cache допускается
только для checks с явно чистым повторным использованием и полным ключом subject+
plan+oracle+runner+environment+permissions. Health живого сервиса, fault injection,
финальная интеграция и causal evaluation не закрываются старым cache hit.
Удаление evidence делает зависимый допуск непроверяемым, а не молча действующим.

## 12. Ресурсы, стоимость и полезные режимы — TST-12

В workflow используется общий бюджет ORC-08 и резерв обязательной проверки;
никакого скрытого дополнительного бюджета «для тестов» нет. Standalone test plan
имеет собственный явно видимый бюджет. Проверки моделей используют тот же endpoint
pool, что исполнители; ожидание слота не равно timeout уже начатого inference.
Зависимые проверки стартуют после их входов, а независимые — при наличии ресурсов.
Одна и та же изменяемая БД/окружение не выдаётся параллельно несовместимым checks.

Начальные предлагаемые defaults standalone-плана: два runner одновременно,
одна тяжёлая Docker/browser проверка, один inference на endpoint; 15 минут общего
deadline, 120 секунд на обычный check, 300 секунд на тяжёлый. Лимит журнала —
2 MiB на поток попытки; при превышении ставится truncation flag. Критическое
структурированное evidence имеет отдельный лимит 8 MiB: превышение не обрезается
до ложного pass, а даёт inconclusive. Ограничения CPU/RAM/диска фиксируются в
выбранном sandbox-профиле и проверяются preflight, не притворяются доступными
на неподдерживаемой платформе. Для research явно задаётся отдельный профиль;
эти defaults не урезают молча объявленную экспериментальную матрицу.

Режимы ценности: быстрые проверки изменённых частей; полный регрессионный прогон;
проверка перед интеграцией; воспроизведение конкретного сбоя; сравнение контроллеров;
проверка надёжности с отказами. Быстрый режим не заменяет финальный набор.
Пользователь может заранее увидеть план, ограничения и оценку расхода без запуска
проверяемого кода. Отчёт объясняет минимальный воспроизводимый сбой и показывает,
что изменилось относительно baseline, не изменяя исходный тест автоматически.

## 13. Проектируемые интерфейсы и экран проверки — TST-13

Следующие API и CLI **предлагаются**, в текущем runtime их нет:

Уже реализован отдельный начальный вход `flycode verify --repo PATH --output PATH`
с `--timeout`, `--reruns 0..2` и `--trust`. Он запускает только локальный
зарегистрированный pytest suite и не заменяет будущие интерфейсы ниже.

| Интерфейс | Назначение |
|---|---|
| `POST /api/verification/plans` | Зафиксировать план по server-owned subject/profile IDs; version и idempotency key обязательны |
| `POST /api/verification/plans/{id}/commands` | `start/cancel/rerun`; expected version и idempotency key, rerun создаёт новую попытку |
| `GET /api/verification/plans/{id}` | Состояние, обязательное покрытие, бюджет и verdict |
| `GET /api/verification/plans/{id}/events` | SSE с cursor/sequence и восстановлением без дублей |
| `GET /api/verification/plans/{id}/artifacts/{artifact_id}` | Разрешённый текстовый/бинарный отчёт по ID |
| `flycode verify --plan-id ID` | Запуск зарегистрированного плана в доверенном локальном CLI |
| `flycode verify --evidence-id ID --reproduce` | Новая попытка воспроизведения с preflight и прежними ограничениями |

API сохраняет loopback/origin/session-token требования. Клиент не передаёт raw
argv, arbitrary URL или путь к manifest. Доверенная CLI-регистрация профиля
отделена от управления запуском агентом. Публикация отчёта и расширение разрешений
не являются допустимыми самокомандами проверяемой модели.

Экран «Проверки» показывает критерии, required/optional, состояние и длительность,
baseline→patch→integrated результаты, версию проверенного кода и причины блокировки.
Отдельно видны реальные/записанные вызовы моделей, skipped/xfail/flaky, infra errors,
расход/резерв, артефакты и кнопки остановки/воспроизведения. Процент — доля
завершённых обязательных проверок, а не оценка качества или выдуманный ETA.
Код изменился после pass — статус «Нужна повторная проверка». На мобильном экране
остановка и причина неуспеха доступны без горизонтальной прокрутки.

## 14. Совместимость и размещение — TST-14

Предлагается пакет `src/flycode/verification/` с модулями `plan`, `snapshot`,
`engine`, `runner`, `sandbox`, `oracle`, `verdict`, `evidence`; контракты — в
`domain/verification.py`. Адаптеры подключают существующие `tools/tests.py`,
`environment/`, `research/`, `telemetry/` и `web/`. Новые имена — проектируемые файлы,
а не существующий API. Точное разбиение и migration задаются планом реализации.

`run_tests` сохраняет ToolResult-совместимость через адаптер. Расширенное evidence
содержит ссылку на исходный verdict и новый schema version; старые логи читаются
как legacy без выдуманных case IDs, coverage и защищённого completion status.
Переход существующего completion gate на VerificationVerdict делается отдельным
изменением с контрактными тестами, без скрытого переопределения всех старых запусков.

В fingerprint нового допуска включаются verification engine, adapter, oracle,
evaluator и используемые схемы/профили. Исторические v1 admissions не получают
новые права автоматически. После смены проверяемого runtime evidence пересоздаётся.
Обычный failed test или неверный target остаются исходом проверки; инфраструктурные
ошибки учитываются раздельно и очищаются после успешного восстановления той же
службы. Нельзя возвращать append-only смешанный recent_errors, из-за которого
прошедшая исправленная задача никогда не сможет завершиться.

## 15. Приёмка модуля — TST-15

Эти сценарии проверяют сам движок, а не объявляют реализацию готовой.

| ID | Проверяемое поведение |
|---|---|
| TV-01 | PASS валиден только для того же subject/plan/oracle/environment; dirty/untracked изменение и новая база инвалидируют результат |
| TV-02 | Пустой набор, all-skipped/xfail, missing/malformed report и exit/status mismatch не дают pass |
| TV-03 | Assertion failure, collection error, infra failure и timeout различимы; ни один не выпадает из отчёта |
| TV-04 | Rerun сохраняет исходное падение; pass/fail расхождение становится flaky и блокирует обязательную приёмку |
| TV-05 | Агент не удаляет обязательный тест, не расширяет права и не подменяет oracle/manifest; новый agent-written тест идёт отдельно |
| TV-06 | Symlink/path traversal, чужой artifact ID, malicious XML/HTML и чрезмерный отчёт отклоняются без выдачи секретов или исполнения в UI |
| TV-07 | Cancel/timeout прекращает новые запросы, останавливает только собственные процессы и сохраняет частичное evidence |
| TV-08 | Duplicate command и crash до/после отправки или записи manifest не дают двойной попытки/эффекта, ложного pass и принятия старого fencing token |
| TV-09 | Параллельные checks не превышают бюджет/endpoint pool и не получают конфликтующее право на БД; cleanup сохраняет чужие ресурсы |
| TV-10 | Зелёные patch по отдельности не закрывают workflow без тестов объединённой версии; approval другого hash не принимается |
| TV-11 | ORC AC-01..14 исполняются с указанными инъекциями; успешный fault-сценарий не считается успешным repair |
| TV-12 | Frozen learning, neural scores, topology и shadow соответствуют контрактам; replay/mock не подменяют живые измерения |
| TV-13 | Setup-failed/timeout остаются в матрице, splits не пересекаются, бюджеты сопоставлены, null results и интервалы сохранены |
| TV-14 | Изменённый/удалённый evidence и неверный scope отклоняют admission; старый v1 не разрешает multi-agent dispatch |
| TV-15 | Legacy ToolResult/history читаются; failed-test feedback не превращается в вечный infra error после исправления |
| TV-16 | UI/SSE восстанавливают отчёт без дублей, показывают flaky/skip/invalidated; мобильная остановка доступна |
| TV-17 | Negative control/mutation подтверждает чувствительность критических oracle; фиктивный зелёный stdout не заменяет обязательные наблюдения |

Для базовой поставки все TV сценарии, относящиеся к включённым runners, должны
пройти на явно указанной платформе; неподдерживаемый runner заблокирован и
не называется проверенным. Для Docker/browser/LMStudio и реального коннектома
нужны отдельные opt-in живые прогоны. Пропуск из-за отсутствия данных честно
фиксируется, но не закрывает соответствующую приёмку.

## 16. Этапы и пример использования

Нумерация продолжает основной roadmap; это предлагаемая разработка.

| Фаза | Поставка | Требования и приёмка |
|---|---|---|
| 21 — Основа проверки | Снимки, планы, pytest adapter, структурированные результаты и базовый verdict | TST-01..05,07,14; TV-01..03,15 |
| 22 — Достоверность и изоляция | Независимые oracle, sandbox-профили, flaky policy, evidence и отмена/восстановление | TST-04..08,11,12; TV-04..09,17 |
| 23 — Проверка команды | Связь с task DAG/review/integration, event harness и fault injection | TST-09,12; TV-09..11 |
| 24 — Исследовательская валидация | Адаптеры connectome/replay/benchmark, splits, агрегаты и scoped admission | TST-10,11,14; TV-12..14 |
| 25 — Рабочее место проверки | CLI/API, экран, воспроизведение, экспорт и отчёты | TST-11..13; TV-06,07,16 |

Номера — порядок описания, не требование сначала закончить весь §100.
Фазы 21–22 развиваются на существующем одиночном агенте и нужны перед приёмкой
изоляции/интеграции multi-agent фазы 17. Фаза 23 использует готовые части фаз
16–17; фаза 24 — 18–19. Экран проверки фазы 25 может развиваться вместе с фазой
20. Так не возникает зависимости «сначала допустить оркестрацию, затем научиться
проверять её допуск».

Пример: два агента подготовили обработчик фильтра и тесты по общему контракту.
Модуль фиксирует base и оба patch, подтверждает чувствительность новых тестов
на исходном дефекте, выполняет проверки patch и общего snapshot. Если API-тест
проходит, а неизвестный статус ломает совместимость, verdict содержит failed
criterion и ссылки на воспроизводимый пример. После исправления создаётся новая
попытка на новом snapshot; прежнее падение остаётся в истории. Только актуальный
объединённый pass разблокирует завершение workflow. Сравнение fly scheduler с
обычным scheduler проводится отдельной серией с равным бюджетом, а не выводится
из одного успешного исправления.
