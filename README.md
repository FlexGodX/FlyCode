# FlyCode

[English](README.en.md) · **Русский**

FlyCode — экспериментальный автономный агент для исправления кода. Он читает
файлы проекта, предлагает небольшие изменения, выбирает действие через
контроллер, вдохновлённый вычислительными механизмами мозга дрозофилы, и
проверяет результат тестами и состоянием приложения.

**Статус: рабочий MVP до фазы 4 включительно.** Агент самостоятельно исправляет
учебный FastAPI/PostgreSQL-проект, запускает Docker Compose, применяет миграции
Alembic и проверяет API. Доступны реальный граф FlyWire, его сокращённая версия
и офлайн-процедуры обучения, память, наблюдатель и защищённый автономный режим
с узким допуском. Исследовательские критерии описаны ниже.

## Что умеет MVP

- Читать, искать, создавать и редактировать файлы, смотреть Git status/diff.
- Запускать тесты и выполнять ограниченный набор Docker/Postgres/Alembic/HTTP-инструментов.
- Выбирать действия с помощью Functional Fly или базовых контроллеров.
- Учитывать рабочую и эпизодическую память, новизну, повторение действий и результат выполнения.
- Блокировать известные опасные действия через safety mask.
- Завершать задачу только после необходимых проверок. Правки и перезапуск
  стека сбрасывают предыдущие подтверждения готовности.

По умолчанию используется **детерминированный эвристический генератор**: ему
не нужен API-ключ, но он решает только поддерживаемые учебные случаи. Для
семантического разбора других проектов можно подключить LLM.

## Установка

Проверенная версия Python — **3.12**. Для простого примера Docker не нужен.
Для демонстрации с сервисами требуются работающий Docker Engine и Docker Compose.

```bash
git clone https://github.com/FlexGodX/FlyCode.git
cd FlyCode
python3.12 -m venv .venv
source .venv/bin/activate
python -m pip install -e .
flycode brains
```

В PowerShell окружение активируется командой `.venv\Scripts\Activate.ps1`.

## Интерфейс агента

```bash
flycode ui --workspace . --port 8790
```

Откройте **http://127.0.0.1:8790**. Нужен только установленный FlyCode: Node.js,
сборка интерфейса и внешний сервер не требуются.

Дополнительный [desktop-интерфейс](http://127.0.0.1:8790/desktop) предлагает
компактную навигацию, светлую/тёмную тему и сворачиваемые панели. Классический
интерфейс остаётся на `/`; между вариантами можно переключаться в боковой панели.
Оба используют общие проекты, чаты, историю и настройки моделей.
Проект можно связать с любой локальной папкой без Git через системное окно выбора
или создать чат «Без проекта», файлы которого хранятся отдельно.

- **«Попробовать на демо»** запускает реальное исправление учебной ошибки без моделей.
- Для своей задачи выберите проект, опишите результат и нажмите стрелку или
  `⌘ Enter` / `Ctrl Enter`. По умолчанию используются локальные Qwen + Jev.
- В диалоге видны обоснования выбранных действий, вызовы моделей, инструменты и
  результаты проверок. Раскройте «Почему это действие», чтобы сравнить кандидатов
  и оценки Jev; вкладка «Изменения» показывает успешно применённые правки.
- Во вкладке «Журнал» доступны поиск, фильтры по источнику и ошибкам, время и
  номера событий/шагов. Раскройте событие для просмотра JSON; «Следить» управляет
  прокруткой. «Скачать JSONL» выгружает весь записанный журнал выбранного чата.
- Панель справа подсвечивает текущий этап и показывает режим, уверенность
  контроллера, риск, шаги и число реальных вызовов моделей. На узком экране она
  открывается кнопкой в правом верхнем углу.
- Кнопка моделей открывает выбор основной модели и необязательного оценщика.
  Отключите «Дополнительная оценка вариантов», чтобы использовать Qwen без Jev.
  Справа отдельная кнопка параметров: коннектом, память, seed, шаги, бюджеты и тайм-аут.
  «Остановить» дожидается текущего вызова; новые действия после остановки
  не запускаются. Уже применённые правки сохраняются.

`--workspace` задаёт начальную папку интерфейса. Другие локальные папки можно
добавить через раздел «Проекты». **Агент изменяет файлы выбранного проекта напрямую**;
демонстрация всегда создаёт отдельную папку и не пересоздаёт ваш проект.
Одновременно выполняется одна задача. Интерфейс доступен только на локальном
компьютере и не публикуется в интернет.

История и события хранятся в `~/.local/share/flycode/ui`; `--data-dir PATH`
позволяет выбрать другое место. Для демо файлы находятся в
`<data-dir>/<run-id>/repository`. Обновление страницы восстанавливает журнал;
после перезапуска сервера незавершённые задачи помечаются прерванными.
Обоснования — это краткие объяснения действий, не скрытая цепочка мыслей модели.
Схема показывает выбранный контроллер и вызовы компонентов; для `full` доступны сведения о реальном графе.
Большие результаты инструментов в интерфейсе сокращаются до 16 000 символов.

Внутренняя основа командной очереди использует общие Pydantic-контракты и одну
SQLite-базу для задач, исполнителей, попыток, бюджетов и событий. Назначение и
резервирование атомарны; повтор команды не создаёт дополнительный расход,
а перезапуск сохраняет неподтверждённого исполнителя до сверки. Tracker читает
эту же базу. Внутренний runtime уже выполняет попытки в отдельных процессах;
подключение очереди к CLI/API и экранам ещё не завершено;
текущий интерфейс продолжает выполнять одну задачу. Проверяемый статус — в
[плане поставки](docs/superpowers/plans/2026-10-16-specification-delivery.md).
Адаптер модельных запросов резервирует endpoint и учитывает расход до HTTP,
сохраняет доступный token usage и удерживает неизвестный исход после тайм-аута.
Ожидание можно отменить без отправки запроса. Одиночный/парный cortex, прямые
клиенты и явные probes используют тот же индекс занятости endpoint в SQLite
(schema11). Все исполнители должны использовать одну базу через
`FLYCODE_STATE_DATABASE`; по умолчанию это `~/.local/share/flycode/state.sqlite`.
Неизвестный результат удерживает endpoint после перезапуска до доверенной сверки;
занятый probe возвращает409 без вызова модели. Поздний ответ после Stop сохраняет
usage, но не возвращает кандидатов. Это общий допуск к ресурсу, а подключение
канонической очереди к интерфейсу и dispatcher остаётся открытым.

`AttemptCortex` связывает существующий `run_agent` с целью, критериями и
модельным бюджетом канонической попытки. Допуск закрепляет фактически загруженный
instance и его контекст из LM Studio; смена конфигурации требует новой проверки.
Консервативная граница размера запроса блокирует переполнение до HTTP, но не
заменяет точный токенизатор. Каноническая цель передаётся один раз; точные повторы
фактов закреплённых входов удаляются только из копии контекста с сохранением
последнего порядка, всех уникальных версий, ошибок и provenance. История действий
не меняется; переполнение уникальными данными по-прежнему блокируется.
`AttemptEnvironment` проверяет разрешения
и пути, списывает бюджет до каждого инструмента и сохраняет его фактический
исход. Повтор не выполняет действие снова; неизвестный исход удерживает попытку.
Адаптер пока требует чтение всего проекта и поддерживает локальные файловые
инструменты/pytest. Это контроль доверенной копии, не песочница для чужого кода.

`Runtime` запускает существующий `run_agent` в собственной группе процессов;
модельные HTTP-запросы обслуживает отдельный поток хоста. Heartbeat10с/lease30с
не зависят от ожидания модели. Stop завершает принадлежащую исполнителю группу,
а незавершённый HTTP или неизвестный исход pytest удерживают попытку до сверки.
`Workspaces` фиксирует dirty/untracked байты и права в отдельном checkout без
настроек/hooks пользователя. После подтверждённой остановки `Artifacts` публикует
patch с хешами точных байтов и прав. Отдельная reviewer-попытка выполняет
зарегистрированные владельцем проверки; каждый реальный pytest расходует общий
бюджет. Единственный host-integrator проверяет объединённую копию, применяет
разрешённый patch и заново проверяет исходную папку перед `succeeded`.
Применение требует нативного атомарного обмена/исключительного переименования;
исходные файловые объекты сохраняются вне проекта, включая конкурентные правки.
Worker и host-проверка не могут разделить одну попытку. Завершённый результат
связан с точными файлами, критериями, review и доказательствами: изменение этих
данных снимает `succeeded` перед чтением tracker или новым назначением. Заголовок,
tags и архив сохраняют корректные доказательства. Команда `reopen` создаёт новую
проверяемую версию, сохраняя попытки, расход и исходный срок workflow. Повторный
review требует новых проверок; совместимый уже применённый результат проверяется
без повторной записи файлов и без изменения исторических попыток. Старые базы без
данных актуальности сохраняются, но их завершение требует повторной проверки.
Зарегистрированные host-проверки получают отдельного supervisor и durable receipt
остановки всей группы процессов. После сбоя `Integration.reconcile` исключает живого
координатора и проверяет владение процессами перед откатом. Неизвестные внешние
эффекты удерживают назначение до доверенной сверки; остановка группы не заменяет
эту сверку. Отдельный reviewer сохраняет привязку входа/oracle и объект владения
координатором до запуска проверок. `Reviews.reconcile` не допускает повторный
запуск той же попытки и освобождает её только после подтверждения остановки
координатора, всех проверок и сверки эффектов. Старые незавершённые review без
таких доказательств остаются заблокированными; положительный verdict не создаётся.
Поздние записи через старые дескрипторы сохраняются, подмена файла
пользователем блокирует откат. Это внутренняя основа для доверенных локальных
проектов: dispatcher и подключение CLI/API/UI ещё не завершены.
Вывод ошибок worker сохраняется отдельно от рабочей копии с пределом64КиБ;
события содержат ссылку, хеш, размер и признак усечения, без текста ошибок.
Конфликт проверенных patch сохраняет обе версии и создаёт один черновик
согласования с закреплёнными хешами и базой. Черновик требует критериев, прав и
бюджета владельца; повтор после перезапуска не создаёт новую задачу и не расходует
модель. При достижении лимита задач сохраняется явная блокировка. Несовместимое
объединение даже по отдельности зелёных patch блокируется до записи в исходную
папку. Одобренный владельцем исполнитель читает обе закреплённые версии через
host-маршрут `read_file` с явным ID artifact; каждое чтение расходует один вызов
инструмента. Проверяются хеши и пути; поддержаны UTF-8 файлы до3 500 байт, бинарные
и более крупные файлы дают явный отказ. Источники данных сохраняются в памяти
после правок рабочей копии.
Контекст сохраняет закреплённые данные, прочитанный текст рабочей копии и ошибки;
необязательная история сокращается. Если обязательные данные не помещаются,
запрос блокируется до HTTP. Новый patch требует независимого review и проверок
объединённой копии и исходной папки по всем первоначальным требованиям.
Исторические failed/interrupted попытки не меняются. Повторное открытие корневой
задачи требует свежего review и всех проверок с прежним deadline и расходом.
Повторно использовать исходные review неизменяемых patch можно только при
неизменных критериях и точной привязке к предыдущему результату.

Адресованные сообщения используют ту же SQLite-базу: повторная доставка,
подтверждения и ответы на вопросы учитываются атомарно. Лимиты workflow —200
доставок,16KiB на конверт, до3 явных адресатов, TTL до5минут и до4 пересылок.
Поздний ответ не переносится в новую попытку. При явно разрешённых связях worker
передаёт фактическую активность коллеге; модель получает ограниченные выдержки
с источником и ревизией. Нехватка контекста откладывает сообщение, а не останавливает
обычный запрос. Сообщения не выдают права и не подтверждают выполнение задачи.
При разрешении `send_message` и явных связях хоста модель может выбрать отправку
типизированного сообщения. Действие проходит через RPC, проверку адресатов и общий
бюджет инструментов; повтор после смены хоста не списывает расход заново.
Вопросы и принятые ответы доступны последующим решениям в пределах срока и прав;
уведомления об активности уступают им место в контексте. Интерфейс переписки и
диспетчер ожидания дочерних задач ещё не подключены. После ответа модели срок и
права сообщений проверяются снова; устаревшее решение не допускается к действию.

## Первый запуск без API-ключа

```bash
flycode run \
  --repo /tmp/flycode-toy \
  --fixture toy_arithmetic_bug \
  --task "Fix the bug" \
  --brain functional \
  --control bias
```

Агент создаст учебный проект с ошибкой, исправит его и запустит тесты. При успехе
вывод содержит `success=True`, а процесс завершается с кодом `0`.
Для примера с отсутствующим импортом используйте `--fixture toy_import_bug`.

**Каталог, переданный вместе с `--fixture`, пересоздаётся. Используйте отдельный
временный каталог, а не существующий проект.** В Windows замените `/tmp/...`
на путь к своему временному каталогу.

## Демонстрация: исправить и запустить FastAPI + PostgreSQL

Убедитесь, что Docker работает и порт **8000** свободен. PostgreSQL доступен
внутри сети Compose; свободный порт 5432 на хосте не требуется. При первом
запуске нужен интернет для загрузки образов и зависимостей.

```bash
docker info
docker compose version

flycode run \
  --repo /tmp/flycode-environment \
  --fixture fastapi_postgres_app \
  --task "Fix this FastAPI application and get it fully running" \
  --brain functional \
  --control bias \
  --max-steps 60 \
  --max-tool-calls 60

curl --fail http://localhost:8000/health
curl --fail http://localhost:8000/users
```

В примере намеренно сломаны конфигурация порта, путь миграций, обращение к
переменной окружения, маршрут API и Python-импорт. Агент выводит исправления из
прочитанных файлов и результатов инструментов. Затем он собирает контейнеры,
проверяет PostgreSQL, выполняет миграцию и тесты внутри контейнера приложения
и проверяет `/health` и `/users` по HTTP.

Приложение продолжает работать после завершения агента. Чтобы остановить его:

```bash
docker compose --project-directory /tmp/flycode-environment down
```

## Настоящий коннектом FlyWire — фаза 5

```bash
python -m pip install -e '.[research]'
flycode connectome download
flycode connectome prepare --source ~/.cache/flycode/flywire-783
flycode connectome info
flycode run --repo /tmp/flycode-full --fixture toy_arithmetic_bug \
  --task "Fix the bug" --brain full
```

Первая загрузка получает два официальных файла, около 853 МБ, и проверяет
контрольные суммы. Источник: [FlyWire Consortium, v783, CC BY 4.0](https://zenodo.org/records/10676866).
Данные остаются в локальном кеше и не входят в репозиторий.

Подготовленный граф содержит все **139 255** опубликованных нейронов и
**2 700 513** направленных связей после объединения областей и порога
в 5 синапсов. `--connectome-path PATH` или `FLYCODE_CONNECTOME_PATH`
позволяет выбрать подготовленный граф. При отсутствии данных случайной
подмены не происходит: запуск завершается с ошибкой.

В интерфейсе выберите «Нейронный контроллер → FlyWire 783» в настройках.
К нему подключаются те же Qwen и Jev; нейронное состояние участвует в
маршрутизации вызовов и оценке действий. В плане название Hermes обозначает
сам FlyCode — приложение, в котором работают эти агенты.

Это исследовательская модель: реальная топология работает с приближённой
рекуррентной динамикой, программно заданными входами/выходами и начальным
приоритетом этапов работы. Знаки связей оцениваются по нейромедиаторам;
GABA/GLUT считаются тормозящими, остальные — возбуждающими. Это допущение,
не полная биофизическая симуляция. Старый `frozen_connectome` сохранён как
эксперимент со случайной проекцией. Преимущество перед Functional Fly ещё
не доказано; измерения обучения и уменьшения графа приведены ниже.

## Офлайн-обучение, сокращение графа и перенос поведения

Сначала запишите успешные запуски. В обучение попадают **все** действия из
выбранной папки: перед использованием проверьте траектории. Новые эпизоды
распознаются по файлам и сбросу номера шага; состояния между ними не смешиваются.

```bash
flycode run --repo /tmp/flycode-teacher-add --fixture toy_arithmetic_bug \
  --task "Fix the bug" --brain functional --telemetry-dir ~/.cache/flycode/training-records
flycode run --repo /tmp/flycode-teacher-import --fixture toy_import_bug \
  --task "Fix the bug" --brain functional --telemetry-dir ~/.cache/flycode/training-records

flycode train --trajectories ~/.cache/flycode/training-records \
  --output ~/.cache/flycode/checkpoints/constrained
flycode run --repo /tmp/flycode-trained --fixture toy_arithmetic_bug \
  --task "Fix the bug" --brain full --checkpoint ~/.cache/flycode/checkpoints/constrained

flycode connectome reduce --source ~/.cache/flycode/flywire-783/prepared \
  --neurons 4096 --output ~/.cache/flycode/reduced-4096
flycode run --repo /tmp/flycode-reduced --fixture toy_arithmetic_bug \
  --task "Fix the bug" --brain reduced --connectome-path ~/.cache/flycode/reduced-4096

flycode distill --trajectories ~/.cache/flycode/training-records \
  --teacher-checkpoint ~/.cache/flycode/checkpoints/constrained \
  --output ~/.cache/flycode/checkpoints/student
# Только после успешной проверки distill:
flycode run --repo /tmp/flycode-student --fixture toy_arithmetic_bug \
  --task "Fix the bug" --brain functional --checkpoint ~/.cache/flycode/checkpoints/student
```

`train` подбирает усиление рекуррентных связей и скорость обновления состояния,
обучает выходные оценки инструментов. Матрица связей неизменна; входы, выходы,
параметры динамики и контрольные суммы сохраняются в отдельном checkpoint.
`training.json` содержит ошибки подражания и точность до/после обучения.
Это оценка на обучающих примерах, не доказательство улучшения решения задач.

`connectome reduce` выбирает связный участок существующего графа и наследует
соответствующие входы и выходы полной модели. Новые связи не создаются;
`--checkpoint PATH` позволяет использовать обученные параметры родителя.

`distill` переносит **оценки инструментов** в небольшой выходной слой Functional Fly;
выбор режима поведения остаётся прежним. Целые эпизоды выделяются для проверки.
По умолчанию нужны RMSE ≤ 0,1 и совпадение лучшего инструмента ≥ 90%; параметры
`--max-rmse` и `--min-agreement` задают допуск до эксперимента. При непрохождении
команда возвращает код 1 и сохраняет отчёт; такой checkpoint нельзя включить.
Эти исследовательские команды сейчас доступны через CLI.

Вторая версия студента использует 784 параметра и квадратичные признаки;
старые линейные checkpoint остаются совместимыми. Проверка воспроизводит
настоящий контроллер с его состоянием и историей действий.

Измерения на этом компьютере: два учебных проекта, seeds 0/1/2, `bias` и `hard`.
[Сводный отчёт](docs/research-results/2026-10-15-adaptation.json) сохраняет условия и результаты.

## Сохранение опыта и исследовательские проверки

Фаза 10: Functional Fly учится только на результатах выполненных действий.
Память сохраняется между задачами; обновления MB/RPE, размер памяти и изменение
политики ограничены. Проверка на сохранённых примерах отклоняет ухудшающие
обновления и восстанавливает снимок политики. По умолчанию обучение выключено.

```bash
flycode run --repo /tmp/flycode-learn-add --fixture toy_arithmetic_bug \
  --task "Fix the bug" --learning-memory ~/.cache/flycode/experience
flycode run --repo /tmp/flycode-learn-import --fixture toy_import_bug \
  --task "Fix the bug" --learning-memory ~/.cache/flycode/experience

flycode benchmark --config docs/examples/benchmark.json \
  --output ~/.cache/flycode/benchmarks
flycode lesion --trajectories ~/.cache/flycode/training-records \
  --checkpoint ~/.cache/flycode/checkpoints/constrained --fraction 0.1 \
  --output ~/.cache/flycode/lesion.json
flycode sensitivity --trajectories ~/.cache/flycode/training-records \
  --checkpoint ~/.cache/flycode/checkpoints/constrained \
  --parameter recurrent_gain --values 0.6 0.9 1.2 \
  --output ~/.cache/flycode/sensitivity.json
```

Для обучения без сохранения на диск используйте `--learn`. Сохраняйте прежний
`--seed` при загрузке опыта: файл связан с проекцией признаков. Счётчики проверки
обновлений относятся к текущему экземпляру контроллера; число обучений MB
сохраняется. В серии из 36 запусков обучение и замороженный контроллер решили
все задачи за 9 шагов: ускорение адаптации ещё не подтверждено.

`benchmark` создаёт отдельные проекты и журналы для каждого варианта. Поддерживаются
два обучающих примера и отдельные `search_helper_bug` / `boundary_regression_bug`
для проверки поиска помощника и граничных условий. Это синтетические проекты,
а не проверка обобщения на реальные неизвестные репозитории. Поле `cortex`
принимает `heuristic`, исследовательский `tournament` или `lmstudio` с явными
настройками моделей, таймаута и бюджета вызовов. Для сравнения обученной и исходной
модели задайте отдельную конфигурацию на каждый seed и соответствующий checkpoint.
Отчёт показывает фактические затраты; их равенство не предполагается.

Бенчмарк обратной связи от 2026-10-16: [протокол и повторение](benchmarks/feedback-v1/README.md),
[полный отчёт](docs/validation/2026-10-16-feedback-benchmark.md). В 280 офлайн-запусках
проверены пять исходных контроллеров и два обученных варианта, 5 seeds, 4 семейства
задач, режимы bias/hard; все запросы на английском. Первая попытка обучения ухудшила
результат и сохранена в отчёте. Повторное обучение по успешным коротким траекториям
подняло решение простых задач Full Fly с 14/20 до 20/20; переноса на отложенные
задачи с эвристическим cortex нет. Исходный граф сохранён, checkpoints доступны
отдельно и не меняют настройки приложения. Это не научный или production-допуск.
В шести реальных запусках с Qwen исходный Full Fly решил 2/2 задачи, первый
обученный вариант — 1/2, повторно обученный — 0/2. Обученные варианты отклонены
для замены исходного контроллера; рост тренировочной точности не скрыл регрессию.

Фаза 11 реализована частично: отключение входов/связей выбранных нейронов и
чувствительность параметров измеряются на записанных траекториях. Структура
графа сохраняется, исходные файлы не меняются. `counterfactual_task_success`
остаётся `null`: эта команда не решает задачу повторно. Чтобы выполнить
настоящий ремонт с повреждённой сетью, задайте `lesion_fraction` в конфигурации
`benchmark`: исходный граф не меняется, отчёт сохраняет маску и число активных связей.

Повторяемые эксперименты теперь запускаются отдельной командой. Для каждой
инициализации она сравнивает замороженный и обучающийся Functional Fly; папки
проектов и контекст моделей создаются заново, а память контроллера сохраняется
только внутри соответствующей серии. Отчёт содержит отпечатки политики,
откаты, успешность и затраты первого/последнего повторения. Поле
`faster_adaptation_demonstrated` не становится истинным без успешных задач и
снижения вызовов инструментов у обучающейся версии на каждом из минимум трёх seeds.

## Теневой наблюдатель — фаза 12

```bash
flycode run --repo /tmp/flycode-shadow --fixture toy_arithmetic_bug \
  --task "Fix the bug" --brain functional --shadow-brain full \
  --telemetry-dir ~/.cache/flycode/shadow-records
```

Рабочий контроллер управляет агентом и вызовами моделей; наблюдатель оценивает
те же варианты с той же маской безопасности и **нулевым влиянием** на выбор.
Поля `shadow_decision` в `*.steps.jsonl` сохраняют оба выбора, совпадение,
разность ожидаемого риска и задержку. Альтернативный успех и число вызовов
не оцениваются. Ошибка наблюдателя записывается и не останавливает рабочего
агента. Доступны `--shadow-connectome-path` и `--shadow-checkpoint`.

На реальном FlyWire обе учебные задачи выполнены за 9 шагов; действия полностью
совпали с запуском без наблюдателя, рекомендации совпали в 12 из 18 случаев.
Наблюдатель доступен в CLI и интерфейсе. Более широкая проверка на новых
проектах остаётся исследовательским критерием.

### Анализ наблюдателя и проверка допуска

`docs/examples/benchmark-admission.json` сравнивает рабочий контроллер,
контроллер с наблюдателем и полный граф на двух учебных задачах с тремя seeds.
После запуска используйте каталог эксперимента, указанный в выводе:

```bash
flycode benchmark --config docs/examples/benchmark-admission.json --output ~/.cache/flycode/admission
flycode shadow-analysis --trajectories /path/to/experiment/trajectories --output ~/.cache/flycode/shadow-analysis.json
flycode validate-rollout --report /path/to/experiment/report.json \
  --controller observed --baseline baseline --mode bounded --output ~/.cache/flycode/validation.json
```

Проверка требует полных парных запусков, успешного завершения без регрессий и
ошибок моделей, минимум трёх seeds, двух задач и 30 рекомендаций для теневого
режима. Журналы, код и параметры связаны контрольными суммами. Начальный допуск
разрешает только ступень 10%; смена модели, графа, checkpoint, задачи или бюджета
требует подходящих измерений. Файл `accepted=true` сам по себе ничего не
разрешает: при использовании проверка выполняется заново. `--mode autonomous`
проверяет результаты `hard` против парного `bias` на том же наборе задач.

## Ограниченное влияние и автономный режим — фазы 13–14

После создания допуска можно запустить совпадающую учебную задачу:

```bash
flycode run --repo /tmp/flycode-bounded --fixture toy_arithmetic_bug \
  --task "Fix the bug" --brain functional --shadow-brain full --influence .1 \
  --validation-report ~/.cache/flycode/validation.json
flycode validate-rollout --report /path/to/experiment/report.json \
  --controller autonomous_full --baseline baseline --mode autonomous \
  --output ~/.cache/flycode/autonomous-validation.json
flycode run --repo /tmp/flycode-autonomous --fixture toy_arithmetic_bug \
  --task "Fix the bug" --brain full --autonomous \
  --validation-report ~/.cache/flycode/autonomous-validation.json
```

Ненулевое влияние ограничено диагностическими действиями: чтением, поиском,
проверкой состояния и логов. Наблюдатель не подменяет редактирование, SQL,
запуск тестов или STOP. Ступени: 0/10/25/50/100%; поправка к оценке кандидата
ограничена `0.2 × влияние`. После неудачного изменённого действия или регрессии
влияние отключается до конца задачи. Это не отменяет уже выполненные действия.
Без фактических вмешательств успешные прогоны не разрешают следующую ступень.

`--autonomous` включает защищённый `hard`-выбор. Если отличающийся от `bias`
выбор терпит неудачу или возникает регрессия, остаток задачи использует `bias`.
Проверки безопасности, бюджеты и проверенное завершение сохраняются.
Обычный исследовательский `--control hard` не заменяет допуск.
Для локальных моделей допуск также привязан к точному тексту инструкции.

В интерфейсе откройте **«Наблюдение, память и допуск»**. Доступны подготовленные
полный/сокращённый графы, обученные checkpoints, student, наблюдатель и память
Functional Fly. Профили разделены по имени, контроллеру и seed; сохранение
атомарное. Журнал показывает рекомендации, фактический выбор, обучение и
переключения на резервный режим. Старые задачи в истории остаются читаемыми.
Каталог артефактов по умолчанию — `~/.cache/flycode`; серверный параметр
`FLYCODE_ARTIFACT_ROOT` меняет его. Клиент выбирает идентификаторы, а не пути.

Текущий допуск охватывает только две учебные задачи, три seeds и эвристический
cortex. Он не разрешает произвольный репозиторий или Qwen/Jev без собственных
парных измерений. Это проверка совместимости доказательств, не механизм
аутентификации против владельца локальных файлов.

[Замеры влияния и автономного режима](docs/research-results/2026-10-16-rollout.json):
36/36 запусков на разных уровнях завершены, но вмешательств — 0; повышение
выше 10% отклонено. В отдельном финальном сравнении защищённый полный граф
завершил 6/6 учебных запусков за 5 шагов, baseline — 12/12 за 9 шагов.
Эти узкие результаты не доказывают общего преимущества.

[Расширенные измерения](docs/research-results/2026-10-15-expanded-evaluation.json)
содержат отрицательные результаты и ограничения начальной проверки помощника.

## Локальные Qwen + Jev в LM Studio

FlyCode поддерживает две локальные модели с разными ролями:

- `qwen/qwen3.5-9b` формирует конкретные варианты действий.
- `jev-style-qwen3.5-2b-decision` оценивает безопасные варианты по вероятностям
  следующего токена в своём родном формате выбора.
- Fly-контроллер управляет вызовами моделей и сохраняет итоговый выбор действия.
  Можно выбрать Functional Fly или подготовленный реальный граф через `--brain full`.

Если модели уже скачаны, загрузите их в LM Studio и включите локальный сервер:

```bash
lms load qwen/qwen3.5-9b --context-length 8192 -y
lms load jev-style-qwen3.5-2b-decision --context-length 4096 -y
lms server start --port 1234

flycode run \
  --repo /tmp/flycode-local \
  --fixture toy_arithmetic_bug \
  --task "Fix the off-by-one bug in add and verify the tests" \
  --brain functional \
  --llm lmstudio \
  --base-url http://127.0.0.1:1234/v1 \
  --model qwen/qwen3.5-9b \
  --decision-model jev-style-qwen3.5-2b-decision \
  --request-timeout 120 \
  --max-model-calls 30 \
  --telemetry-dir /tmp/flycode-local-telemetry
```

Если сервер уже работает, повторно запускать его не нужно. Идентификаторы
моделей берутся из API LM Studio; при несовпадении программа покажет доступные
ID. Имена выше являются значениями по умолчанию для `--llm lmstudio`.
`LMSTUDIO_BASE_URL` задаёт адрес сервера, а `LMSTUDIO_API_KEY` — ключ, если
в LM Studio включена аутентификация. Облачный API автоматически не используется.

Для одной основной модели добавьте `--no-decision-model` вместо
`--decision-model ...`. Jev при этом не нужен: его клиент не создаётся и запросы
к нему не выполняются. В JSON API явный `"decision_model": null` отключает
оценщик; отсутствие поля сохраняет прежнюю пару по умолчанию.

Другие совместимые модели того же LM Studio выбираются в той же панели.
«Обновить список» не вызывает inference; явная проверка выбранной роли делает
один запрос с тайм-аутом 30 секунд и показывает расход и результат. Основная
роль требует структурированных действий, оценщик — вероятностей вариантов.
Проверка протокола не доказывает качество модели; версия весов может быть неизвестна.
Начальная пара имеет встроенный профиль совместимости, другие модели перед
применением проверяются явно. Выбор сохраняется для следующих задач; просмотр
старого запуска показывает его фактические модели, сохраняя личный выбор.

Контроллер пропускает модели при подтверждённом завершении, своей блокировке
или простой проверке тестов в режиме VERIFY. При уверенности не ниже 0.8 Jev
не вызывается. В `hard` итоговое ранжирование принадлежит контроллеру, поэтому
запрос Jev также пропускается. Safety mask проверяет действия независимо от
оценок моделей. При отказе Jev сохраняются предложения Qwen с диагностикой;
при отказе Qwen агент останавливается без выдуманного исправления. Запросы
ограничены тайм-аутом, числом токенов и общим бюджетом; автоматических повторов нет.

В выводе есть строки `[models]` и счётчики `model_calls`. В телеметрии
сохраняются маршрут вызовов, оценки Jev и ошибки. Сводка задачи не вызывает
дополнительный LLM-запрос. Приёмка с установленными моделями включается явно:

```bash
FLYCODE_TEST_LMSTUDIO=1 python -m pytest tests/e2e/test_lmstudio.py -q
```

## Контроллеры и режимы

| Параметр `--brain` | Назначение |
|---|---|
| `functional` / `functional_fly` | Functional Fly: Task Compass, ассоциативная память, новизна и сигналы результата |
| `mock` | Контроллер для тестов |
| `heuristic_fsm` | Базовая конечная машина состояний |
| `random_reservoir` | Базовый случайный резервуар |
| `generic_rnn` | Базовая рекуррентная сеть |
| `reduced` | Сокращённый биологический граф с наследованием параметров родителя |
| `full` | Настоящая разреженная топология FlyWire с приближённой рекуррентной динамикой |
| `frozen_connectome` / `frozen_full_connectome` | Прежние экспериментальные случайные проекции |

`--control bias` — режим по умолчанию: fly-контроллер влияет на ранжирование
предложений. `--control hard` выбирает действие по оценке контроллера.
В обоих режимах действует safety mask.

## Как устроен цикл

```text
Наблюдение → контроллер → кандидаты действий → safety mask
          → выбор действия → инструмент → новое наблюдение
          → проверка результата → завершение
```

Дорогой семантический разбор выполняет LLM либо ограниченный эвристический
генератор. Лёгкий контроллер хранит состояние стратегии и влияет на выбор
действий. Тесты, сервисы и миграции дают проверяемую обратную связь.

## Проверки

Для отдельной проверки доверенного локального Python-проекта:

```bash
flycode verify --repo /path/to/project --output /tmp/flycode-verification
```

Команда копирует разрешённые входы, запускает зарегистрированный pytest-профиль
и возвращает JSON-вердикт. `passed` даёт код выхода 0; failure, пустой набор,
skipped/xfail, flaky, timeout и неполное evidence не дают успешного выхода.
`--reruns 1` сохраняет обе попытки; удачный повтор не стирает первое падение.
В папке evidence находятся snapshot/plan, manifest с хешами, вердикт, JUnit и
наблюдённые cases. Изменение входных байтов, executable modes, среды или runtime
инвалидирует прежнюю проверку. Тесты исполняются в отдельной копии.
Корень тестов и конфигурация закреплены внутри снимка; настройки и conftest
родительских каталогов не меняют состав и идентификаторы проверок.
При выборе подпапки Git-репозитория снимок и его инвентарь ограничены этой
подпапкой; имена соседних файлов не включаются.

Доверенный Python-хост может отдельно утвердить `AcceptanceContract` и oracle bytes,
собрать `PlanBuilder` для baseline/target/regression/integration и вызвать
`VerificationEngine.verify_plan`. Такой verdict имеет scope `acceptance-contract`,
покрытие точных критериев и case IDs; новый owner contract отзывает старое одобрение.
Standalone CLI сохраняет scope `registered-suite`. Подробности — в
[спецификации проверок](docs/specs/testing-module.md).

Live single/dual smoke на LM Studio прошли: single использовал 3 запроса Qwen
без оценщика, dual — 3 Qwen + 3 Jev. Оба исправили fixture и отдельно прошли
acceptance plan с неизменными утверждёнными тестами. [Результаты и границы](docs/validation/2026-10-16-model-selection.json).

Standalone CLI проверяет зарегистрированный набор,
а не автоматически все критерии пользовательской задачи. Процессная копия
предназначена для доверенного кода и не ограничивает доступ к сети/хосту.
`--trust untrusted` блокирует запуск до появления поддерживаемой песочницы.
Профили Docker/HTTP/browser, внешние black-box oracle, UI проверок и командный
completion gate остаются в [плане поставки](docs/superpowers/plans/2026-10-16-specification-delivery.md).

```bash
python -m pytest -q
python -m pytest tests/e2e/test_environment_autonomy.py -q
FLYCODE_TEST_CONNECTOME=1 python -m pytest tests/e2e/test_real_connectome.py -q
```

Актуальный результат общего прогона указан в [статусе проекта](docs/handoff.md);
приёмка LM Studio и реального графа включается отдельно.
Приёмочные Docker-тесты действительно запускают агента с Docker/Postgres в режимах `bias` и
`hard`, проверяют HTTP и ревизию Alembic в базе. Они выбирают свободный
HTTP-порт и удаляют свои контейнеры после завершения. Без Docker/Compose
эти два теста явно пропускаются.

Проверки Ruff/mypy для всего проекта пока не проходят: остаются замечания
по стилю и типам. Подробности — в [статусе проекта](docs/handoff.md).

## Ограничения и дальнейший план

- Эвристический генератор не является универсальным исправителем кода.
- Преимущество fly-контроллера над сопоставимыми FSM/RNN пока не доказано.
- Приёмка фаз 6–8 ограничена учебными задачами; обобщение ещё не проверено.
- Фаза 10: механизм обучения готов, ускорение адаптации на задачах не доказано.
- Фаза 11: нужны другие коннектомы, сопоставимые вычислительные бюджеты и новые проекты.
- Фаза 12: нужен более широкий сбор телеметрии на реальных задачах.
- Фазы 13–14 реализованы с узким допуском; широкая автономность и причинный выигрыш ещё не подтверждены.
- Интерфейс поддерживает локальные артефакты, наблюдателя, память и проверяемые режимы.
